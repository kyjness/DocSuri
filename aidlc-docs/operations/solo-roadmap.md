**목표는 두 에이전트를 각자의 임무에서 완성하는 것**이다. 아키텍처 결정:
[requirement-verification-questions-agent-rearchitecture.md](../solo-agent/requirement-verification-questions-agent-rearchitecture.md) (2026-07-18 확정, Q1~Q8).

## 착수 순서 (2026-07-25 확정)

**⑤2 → ⑤3 → ⑥ → ⑧ → ⑩ → ⑪.** 로드맵 번호 그대로이며, 단계를 건너뛰거나 뒤섞지 않는다.
**⑪ 배포는 2026-08-25에 단계로 올렸다** — 결정(2026-08-13)은 `requirements.md`와
`infrastructure-design.md` §12에 있었는데 **로드맵에 밟을 자리가 없었다.** 그래서 배포를
위해 해야 할 일이 어디에도 목록으로 존재하지 않았고, 대신 `ops/cdk/`를 고치는 것이
배포 준비처럼 읽혔다 — 그쪽은 §12.5가 "이번 배포에 사용하지 않는다"고 정한 보존 기록이다.

**⑨는 ⑩에 흡수됐다 (2026-08-20).** 잔여 수정 2건이 정확히 두 에이전트로 갈리고
(⑨-1 novelty 종료 판단 · ⑨-2 evidence 취소), 둘 다 ⑩이 다시 정하는 것과 같은 자리를 만진다 —
⑨-1은 `domain/loop.py`의 종료 조건(`REQUIRED_ARTIFACT_KINDS`)이고 ⑩은 그 집합의 내용이다.
따로 돌면 같은 함수를 두 번 고친다.

**⑩ 안에서는 evidence를 먼저 한다** — novelty가 `form_evidence`로 evidence를 도구처럼 부르므로
(`novelty/adapters/evidence.py`), evidence가 무엇을 돌려주는 물건인지가 정해져야 novelty의
산출물·게이트·종료 조건을 한 번에 정할 수 있다. 반대는 성립하지 않는다.
아키텍처 질문지 Q3=A("novelty 먼저")는 evidence가 고정 파이프라인이던 시절의 판단이고,
⑥에서 evidence를 에이전트로 다시 쓴 뒤로 전제가 뒤집혔다.

**⑧을 에이전트 수정보다 먼저 두는 이유**: 두 에이전트의 자율 판단("더 찾아볼까 / 이제
충분한가")은 코퍼스가 받쳐줘야 의미가 생긴다. 색인이 1,005편인 상태에서는 종료 판단을 넓혀도
검증이 성립하지 않는다.

**⑤를 먼저 끝내고 ⑥으로 가는 이유**: ⑤1(루프)만 끝난 현재 novelty는 기능이 반쪽이다 —
대화 메시지는 저장되지만 루프가 읽지 않고(`domain/loop.py`에 스티어링 주입 없음), 온디맨드
산출물(방향 제안·실험 계획) 생성 경로가 없다. 이는 v2 기능 정의의 절반에 해당한다
(기능 정의 Q1=X·Q4=B). ⑥은 모듈 전면 재작성이라 기간이 길고, 그동안 반쪽 모듈을 방치하게 된다.
⑤2·⑤3은 루프 코어가 이미 있어 증분이 작다.

**⑤3을 ⑥ 뒤로 미루지 않는 이유**: `view_figure`는 설계상 DocModel/S3 **공용 부품**이므로,
⑥ 게이트의 "figure 도구를 문헌탐색에도 노출할지"가 어떻게 정해지든 도구 자체는 동일하게 만든다
(노출 결정은 레지스트리 등록 여부일 뿐). 미뤄서 절약되는 작업이 없다.

## 단계별 작업 절차

각 단계(⑤2·⑤3·⑥·⑩)를 아래 순서로 돈다. 리뷰는 **커밋 이후**에 돌리고, 지적 반영은
`fix(...)` 별도 커밋으로 남긴다 — 무엇이 리뷰로 바뀌었는지가 이력에 보여야 한다.

|---|---|---|
| 0 | **설계 확인** — 해당 유닛의 frozen 설계 문서 대비 범위 확정 | ⑩은 **설계 문서 선행**(설계 없이 코딩 금지) |

| 3 | 로컬 검증 — `uv run ruff check .` · `uv run pytest` | 서브프로젝트 디렉터리에서 실행 |

**단계별로 추가되는 검증**:

- 에이전트 단계(⑤2·⑤3·⑥·⑩) → **에이전트 루프 체크리스트**(루프 상한·도구 결과의 신뢰
  경계·트레이스·중단 안전성)를 6단계 `/code-review`에서 함께 본다. (`backend/CLAUDE.md`는
  존재하지 않는다 — 종전 참조는 유령이었다. 체크리스트는 이 네 항목이 전부다.)
- 공유 스키마를 건드렸으면 → `cd shared/python && uv run python tools/generate.py --check`
- FE 타입이 파급되면 → `pnpm run gen:types && git diff --exit-code types/`
- 게이트 테스트가 걸리는 유닛이면 → 로컬 스택을 띄우고 **스킵 0**을 확인한다
  (스킵은 통과처럼 보인다 — "게이트 레인" 절 참조).

**리뷰 결과가 서로 어긋나면 코드가 arbiter다** — 리뷰 지적을 그대로 믿지 말고 재감사 후
해결/기각을 근거와 함께 기록한다(③ 잔여 4건 처리 방식).

**아래 표의 번호는 항목이 만들어진 순서이지 착수 순서가 아니다** — 실제 순서는 위 "착수 순서"
표다(⑧ → ⑩). 번호가 큰 항목이 뒤라는 뜻이 아니다.

## 개정 (2026-07-25) — MCP 고정 슬롯 해제

### MCP — ⑤ 2단계 고정 슬롯 해제

**MCP 도입은 독립적으로 결정된 적이 없다.** 관련 문항을 되짚으면:

- 아키텍처 Q1의 한 **선택지 설명문**에 역량 목록(`Tool Calling·Planning·Memory·MCP·멀티 에이전트`)으로
  딸려 들어온 것이 유일한 상위 근거다. 최종 구조를 고르는 문항이지 MCP 도입 문항이 아니다.
- FD 게이트 Q5는 **"MCP를 쓴다"를 전제하고 위치만** 묻는다(포트 뒤 어댑터 vs 루프 직결).
- FD 게이트 Q3은 외부 arXiv 검색을 "⑤ 2단계(MCP)로 미룬다"고만 답한다.

즉 "쓸 것인가"를 정면으로 물은 문항이 없는 채로 로드맵에 고정 단계가 생겼다. 해제한다.

해제 근거(도입을 금지하는 것이 아니라 **고정 일정에서 빼는 것**):

- 외부 도구 3종이 **이미 어댑터로 구현돼 있다** — `adapters/external/github.py`,
  `datasets.py`, arXiv 클라이언트는 u1 ingestion. MCP 교체로 늘어나는 기능은 0.
- 서드파티 MCP 서버에 **GitHub·Notion 자격증명을 위임**하게 된다. `tech-stack-decisions.md`가
  "서버는 신뢰 경계 밖"이라 적어둔 인식이 맞다면, 그 결론은 배포 환경에서 프로세스를 늘리지
  않는 쪽이다.
- 프라이버시 방어선(payload allowlist)은 어느 경우든 **우리 어댑터가 강제**하므로, MCP는
  지켜야 할 경계를 늘릴 뿐 줄이지 않는다.

**따라서**: 외부 탐색 포트의 구현을 MCP로 교체할 **필요가 실제로 생기는 시점**(도구 공급처를
자주 갈아끼우게 되거나, 자작 유지비가 교체비를 넘을 때)에 그때의 근거와 함께 도입한다.
FR-31의 "메커니즘 중립화"는 그대로 유효하다 — 포트 뒤 어댑터라는 위치(Q5=A)도 유효하다.
바뀐 것은 **일정뿐**이다.

용어 경계 — **도구**는 스스로 판단하지 않는 부품(검색·요약·DocModel·figure 조회),
**에이전트**는 스스로 판단하는 단위(문헌탐색·차별화). 단 `form_evidence`는 이 경계에 안 맞는다 —
novelty가 스스로 판단하는 evidence를 자기 도구로 부르고 있다(현행 코드, 단방향).

## ⑤a 범위 축소 (2026-07-20)

당초 계획은 u1 → u2 → u7에 같은 전면 정리를 1회씩 돌리는 것이었으나, u1 실시 후 u2·u7분은 취소한다.

u1에서 실제로 값이 나온 것은 중복 제거 자체가 아니라 **테스트가 없던 자리에서 나온 결함**이었다:
`safe_log_dict`의 API 키·연락처 평문 로깅, `migrate`/`reembed`의 alias 분기, OpenAI 어댑터의 429
재시도 불가 분류, 그리고 테스트가 0건이던 컴포넌트 3종(Postgres control-plane·circuit breaker·
redaction 헬퍼). 순수 중복 제거분은 배포가 은퇴한 현 시점에서 회수 시점이 불분명하다 —
유지보수 비용은 그 코드를 다시 만질 때 절감되는데 u1은 당분간 재작업 계획이 없다.

따라서 u2·u7에는 같은 비용을 들이지 않고, 값이 나온 관점만 옮긴다: **실입력 없이 검증되는 경로가
어디인지 점검하고, 그 자리에만 픽스처·테스트를 추가한다.** 정리는 두 유닛을 다시 만질 때
그 작업에 곁들인다.

**정정 (2026-07-21)**: 위 왕복 테스트 3건은 신설 직후부터 CI에서 스킵되고 있었다 —
`boto3.client()`가 프로세스 전역 `DEFAULT_SESSION`에 자격증명을 **해석 시점에 캐시**하는데,
같은 레인의 `test_assets_rds_real.py`가 monkeypatch로 가짜 키를 넣은 상태에서 먼저 클라이언트를
만들면서 그 캐시를 오염시켰다. monkeypatch는 env를 되돌리지만 이미 해석된 자격증명은 되돌리지
못한다. 스킵은 통과로 보이므로 "왕복이 검증된다"는 위 서술이 그동안 사실이 아니었다.
`tests/conftest.py`의 autouse 픽스처로 테스트마다 세션 슬롯을 비워 해소(307+3스킵 → **310 통과,
스킵 0**). 같은 진단을 다시 늦추지 않도록 `ci.yml`의 모든 pytest 호출에 `-rs`를 붙여 스킵 사유를
로그에 남긴다. AWS 자격증명을 monkeypatch하는 테스트는 저장소 전체에서 그 파일 하나뿐이다.

**여전히 게이트로 남은 1건**: `backend/tests/test_citation_graph.py`의 계약 테스트 — 라이브 Semantic
Scholar API + API 키가 필요하다. CI에 넣으려면 저장소 시크릿이 필요하고 외부 API 장애가 CI를 흔들게
되므로 **넣지 않는다**(판단 종결, 후속 아님).

표기가 달라("Table 2 :" 대 "Table 2:") 비교 전에 떼고, 짧은 캡션("Results")은 표를 특정하지
못하므로 쓰지 않는다. 겹치는 영역이 있으면 기존 신호가 그대로 결정한다(폴백은 가산적).

### ⑧-1 5차 — `/code-review` 지적 수리 (2026-08-08) — ✅ 종결

**1. 패널 그룹 붕괴**(HIGH). 4차 앞 커밋에서 패널 필터를 `img` 요구 → `not _caption_only_float`

손실이 아니라 승격이 좁은 문을 냈던 **원래 상태**다.

**6. 내가 넣은 계수기가 무방비였다**. `_emit_float_placement`가 이웃과 달리 `try/except` 없이,

| 논문 | float 위치 | 옛 소유자 | 새 소유자 | 판정 |

**4. 겹침 조각이 캡션 폴백을 가로챈다 — 측정으로 기각.** `_best_match`가 겹침 `> 0`이면 무엇이든

표와 **조각만** 겹치는 경우가 흔하다"였는데, 50편의 재판독 후보 **89건을 실제로 재보니 조각이

| | |
|---|---|

| 기하 매칭 전무(=캡션 폴백이 도는 경우) | **50 / 89** |

89건 중 0건의 판정을 바꾸고**, 더 올리면 회수율만 깎는다. 코드 변경 없이 근거를 주석에 남겨
종결한다.

**측정**: float 위치 전수 대조에서 **22개 라벨 그룹(약 30개 float)이 17편에서 이동**, float 총계는

### ⑧-1.5 — 파싱 소스 사다리 개편 (2026-08-10 확정) — ✅ 종결 (PR #20 머지)

⑧-2 착수 전에 사다리 자체를 재확정했다(BR-29/BR-30 개정 참조). 브랜치
`feature/u1-parse-source-ladder`, 확정 사다리:

```
arXiv:  ar5iv HTML(품질검사) → arXiv PDF → GROBID(품질검사) → 코퍼스 제외
S2/OA:  PDF → GROBID → 코퍼스 제외          (기존 경로 — 배선만 준비, 기동은 별도)
전문:   ar5iv HTML → PDF 텍스트
제거:   native HTML 전부(doc-model·전문 양쪽), PDF 평문 doc-model
```

결정 근거(실측은 메모리 `parse-source-ladder`와 BR 개정에 기록):

- **native 제거** — 운영 검수에서 화면 품질 불량 반복 확인. 좋은 표본도 있으나(2512.08879의
  표·알고리즘은 GROBID보다 정확했다) 소스 신뢰가 논문마다 갈리는 것 자체가 비용이라 제거로 확정.
- **품질검사를 ar5iv에도** — 깨짐은 LaTeXML 공통(동일 10편에서 ar5iv 3편·native 4편 `ltx_ERROR`).
  기존 가드(본문 500자)는 8,905자짜리 깨진 변환(2502.10208)을 통과시킨다.
- **평문 doc-model 제거** — 섹션 2·문단 2 글자 뭉치를 서빙하지 않는다. GROBID 단이 대신한다.
- **실패=코퍼스 제외** — 색인하지 않고 저장한 전문도 삭제. 본문 없는 검색 결과를 없앤다.
- **S2/OA 폴백 무용** — OpenAlex `locations`가 arXiv 프리프린트에 arXiv PDF만 반환(실측).
  "진 소스 PDF 주소 보존" 안은 폐기. S2/OA는 수집(비-arXiv 발견) 전용.

이후 별도 브랜치로 크롭 프레이밍(캡션·본문 잘라내기 + Algorithm 통째 크롭 — 승인됨)을 처리하고,
**⑧-2 배치는 두 브랜치 머지 후 1회만** 돌린다. 저장소의 native_html 산출물 10,638편은 배치가
자연히 덮어쓴다(서빙은 이미 `_REJECTED_SOURCE_TIERS` 게이트가 막고 있다).

### ⑧-1.6 — 크롭 프레이밍 (2026-08-10) — 진행 중

⑧-1.5로 arXiv 논문의 상당수가 GROBID 단으로 내려오는데, 그 단의 그림·표·알고리즘은 전부
**PDF 페이지 크롭 이미지**로만 화면에 나온다. 그 크롭 영역이 네 가지로 망가져 있었다.
브랜치 `feature/u1-crop-framing`, 규칙은 BR-23a.

**결함과 측정** (리포 TEI 픽스처 3편 + 무작위 50편 스윕, 크롭 스펙 2,111개):

1. **크롭의 10~69%가 캡션 텍스트.** float `coords`는 캡션 줄 나열 + 내용 영역인데 통째로

3. **표 크롭이 다른 페이지를 가리킴.** 2607.16138: float은 p11(캡션 띠), `<table>`은 p12.
4. **알고리즘은 첫 조각만 크롭.** `_append_to_listing`이 텍스트만 합치고 좌표를 버렸다.

2.96~6.32 — 상한 2.0은 그 빈 구간에 둔다. 하한 0.5도 같은 무게다: 벡터 패스로만 그린 그림은
텍스트가 아예 없는데 "텍스트 없음"은 캡션 띠라는 증거가 아니다.

**⑧-2에 딸리는 비용**: 표 크롭이 있는 논문에 pdfplumber `extract_words` 패스가 붙는다
(50편·표 크롭 190건에 20초 — Docling 항에 비하면 작다). 표 크롭이 없으면 열리지 않는다.

### ⑧-1.7 — S2/OpenAlex 경로 기동 검증 (2026-08-10) — 진행 중

u1을 닫으려면 arXiv 경로만이 아니라 이 경로도 실제로 돌려보고 고쳐야 한다. 이 경로는 배선만 돼
있었고 **한 번도 실행된 적이 없었다** — `PostgresControlPlaneStore`가 게이트 뒤에서 아무도 안
돌던 것과 같은 자리다. 돌려봤더니 **6편 중 0편**이 doc-model까지 가지 못했다. 어댑터는 멀쩡했고
(OpenAlex 25건·S2 306건 수확 성공) 실패는 전부 출판사와 대화하는 방식에 있었다. 규칙은 BR-23b.

### ⑧-1.8 — 표 재판독이 못 고치는 것 (2026-08-10) — 진행 중

### ⑧-1.9 — 정리 라운드에서 드러난 것 (2026-08-10)

⑧-1.6~1.8의 변경분에 재사용·단순화·효율·고도 네 각도로 리뷰를 돌렸다. 대부분은 중복·낭비
정리라 **출력이 바뀌면 안 되는 작업**이었고, 그건 테스트가 아니라 같은 캐시(50편)로 잰
before/after가 판정한다:

| 지표 | 정리 전 | 정리 후 |
|---|---|---|
| 크롭 스펙 / 영역 변경 / 미저장 | 2,111 / — / 267 | 2,111 / **0** / 267 |
| 표 총계 / 후보 / 수리 / 빈 표 | 212 / 115 / 60 / 6 | 212 / 115 / 60 / 6 |

크롭은 자산 단위로, 표는 논문 단위로 **차이 0**이다. 회전 라벨 때문에 회수했던 2409.08036도
수리 8건 그대로다.

**성격이 다른 두 건은 정리가 아니라 수리였다.**

- **arXiv PDF에 `%PDF-` 검사가 없었다.** ⑧-1.7에서 S2/OpenAlex에 넣은 그 검사가 1차 소스
  사다리에는 빠져 있었고, arXiv 쪽은 더 나빴다 — 검사 없이 받은 바이트가 `raw_cache_mode`
  = `prefer`에서 **원본 캐시에 PDF로 저장돼** 이후 모든 재파싱에 되살아난다. 랜딩 HTML은
  GROBID 500을 부르고 500은 retriable이라 잡이 재시도 루프를 돌다 DLQ로 간다. 검사와 함께
  "실패분은 캐시하지 않는다"를 BR-23b에 명시했다. 같은 자리에서 신원(User-Agent)도 실었다.
  이 검사가 기존 분류를 `PARSE_FAILURE` → `FETCH_FAILURE`로 옮긴다 — 더 앞에서 잡히고 다른
  소스와 같은 라벨이며, 둘 다 permanent라 재시도·DLQ 거동은 같다.
- **회전 단어 관용이 검증의 증인 자체를 넓히고 있었다.** ⑧-1.8이 `printed_text`가 돌려주는
  문자열에 역방향 판독을 섞어 넣었는데, 그러면 검증자가 "페이지가 실제로 찍은 단어"와 "판독
  방향이 애매해서 덤으로 준 것"을 구분할 수 없다. 가로 페이지가 통째로 회전한 경우 풀이 두
  배가 되고, 그게 회전이 가장 흔한 자리다. `PrintedRegion(text, rotated)`로 갈라서 관용은
  `_proven`이 결정하게 했다(숫자에는 아예 주지 않는다). C-2의 증인은 다시 페이지 그대로다.

**미룬 것 하나** — 표 되키움(`table_body_bbox`)은 렌더 루프의 지역 변수라 `table_repair`의
기하 매처는 여전히 GROBID의 붕괴한 상자를 본다. 옳은 형태는 빌더에서 스펙을 PDF로 한 번
해석해 되쓰는 것인데, 지금 순수하고 PDF를 모르는 `tei_crop_specs`에 PDF 의존을 들이는 일이다.
census 판정상 여기서 되찾을 수 있는 상한은 매칭 실패 4건이라 ⑧-2 이후 별건으로 남기고,
`_best_match`의 cover 통계가 크롭 프레이밍 변경 **이전** 측정임을 docstring에 단서로 남겼다.

**/code-review 라운드 (같은 날)** — 10건 보고, 8건 수리·2건 근거 종결. 배치에서 실제로 터질
것이 셋 있었다:

1. **라이선스 오결합** — `_licensed_pdf_copies`가 위치별 (url, 라이선스) 쌍을 옳게 만들고도
   `_openalex_record`가 한 함수 뒤에서 평탄화해, 폴백이 사본 N을 받아도 레코드는 사본 0의
   라이선스를 기록했다. `_license_url`은 모양 검사라 NC 계열 URL도 통과하고 진짜 게이트는
   primary만 본다. 대체 후보를 **primary와 같은 라이선스로 제한**해 기록이 항상 바이트와
   일치하게 했다(실측: 대체 사본 자체가 50레코드 중 2건).
2. **캐시 읽기가 `%PDF-` 검사를 우회** — 검사 이전에 오염된 캐시 항목이 재파싱마다 그대로
   서빙돼, 검사가 끊으려던 재시도→DLQ 루프가 기존 코퍼스에 살아 있었다. 캐시 히트에도 같은
   검사를 적용하고(오염 = 미스, 재수확이 덮어써 자가 치유), `only` 모드는 네트워크에 절대
   가지 않게 했다. 검사는 `http_limits.is_pdf_payload` 한 곳으로 통합(어댑터 3곳이 사용).
3. **질의 어구가 따옴표 없이 묶임** — `A | B`는 S2 문법에서 인접 단어에 묶여 구가 사라진다
   (S2 자체 문서가 다중 단어 피연산자를 괄호 침). 어구를 따옴표로 감쌌고, 라이브로 확인:
   S2 51만 건(2025~) 정상 합집합, OpenAlex `x_query` 에코가 `stemmed "artificial
   intelligence"`로 구 보존을 직접 보여준다.

나머지: 캡션 매칭을 정렬 허용(재판독 쪽 선행 라벨 무관) + 끝-도달 조건(서두만 공유하는 형제
오매칭 차단)으로 바꿨고, `_widen_crop`에 수직 한계 72pt(실측 이어붙임 간격 0.5·0.6·46.3pt의
위)를 넣었고, 캡션-전용 거부를 로그로 드러냈고(밴드가 회수 불가능한 순수 벡터 그림을 버릴
수 있다는 증거 수집용), `ArxivAssetSource`에 신원·캐시 검사를 붙였고, `_PageTextCache`가
페이지 핸들을 붙들던 것을 닫았다. 종결 2건: S2 대체 사본(API가 `openAccessPdf` 하나만 줌 +
arXiv id 보유분은 dedup이 arXiv로 넘김), 페이지 로드 통합·단계 간 pdfplumber 공유(페이지당
ms 수준 + 아키텍처 변경이라 보류).

판정(같은 50편 캐시): 크롭 스윕 **완전 동일**(2,111/미저장 267 — 수직 한계가 실측 사례를
안 건드림의 증명), 표 재판독 감사도 **논문 단위까지 완전 동일**(212/115/60/6 — 캡션 매칭
강화가 기존 수리를 하나도 잃지 않았다는 증명. 라벨·형제 케이스는 유닛 테스트가 고정한다).

### ⑧-1.10 — 실스택 눈확인 (2026-08-11)

코퍼스를 건드리지 않기 위해 **별도 데이터 루트**에서 했다: s3proxy 볼륨이 이미
`${DOCSURI_S3_MIRROR:-~/data/docsuri-data/s3}`로 파라미터화돼 있어 env 하나로 갈리고,
control plane은 별도 DB(`docsuri_verify`), 색인은 뷰어가 직행 URL을 쓰므로 아예 건너뛴다.
`~/data/docsuri-data`(24GB)는 읽지도 쓰지도 않았다.

경로별로 1편씩, PDF 경로만 2편 — **크롭 변경은 PDF/GROBID 경로에서만 보이기 때문이다**
(ar5iv 경로는 자산을 e-print/구조에서 따로 뽑는다). PDF 경로 논문은 ar5iv 빌드가 없거나
품질검사에 떨어지는 것이어야 우리가 고친 코드에 닿는다.

| 2409.08036 | arXiv PDF→GROBID | Table 9/10/11 = **51·51·50행** (회전 라벨 재판독), 자산 134 |

크롭을 렌더해 직접 봤다. 표 크롭은 머리글부터 마지막 행까지 들어오고 캡션도 이웃 표도 없다
(51행 표가 회전 라벨까지 온전한 것이 결정적). 그림 크롭은 플롯·범례·축이 살아 있고 캡션
문장이 빠졌다.

**캡션-전용 거부 8건은 전부 옳았다** — 모두 `region/caption ≈ 1.00`, 즉 크롭 영역의 텍스트가
캡션과 글자 수까지 같고 상자 높이가 20~53pt다. 내용은 프롬프트 박스·벡터 다이어그램·GROBID가
본문 문단을 float로 오분류한 것. `/code-review`가 우려한 "밴드에 걸린 진짜 그림" 오탐은 0건.

**그리고 결함 하나를 잡았다 — 테스트가 아니라 눈으로만 보이는 종류다.** 패널이 쌓인 그림에서
맨 아래 조각만 크롭됐다(2608.07458 Figure 1: 패널 6개 158pt 중 31pt). 원인은 회수가 캡션에
가장 가까운 그래픽 하나만 집는 것 + 캡션 간격 제한이 위쪽 패널을 후보에서 아예 배제한 것.
앵커 선택과 등반을 분리하고, 등반은 "Figure N"/"Table N"로 시작하는 밴드에서 멈추게 했다 —
간격으로도(패널 16.9pt = 두 줄 캡션), 텍스트 유무로도(패널 사이에 소제목이 인쇄돼 있다)
가를 수 없어서다. 실논문 4편 221스펙 중 변경은 이 1건뿐이다.

운영 메모: GROBID와 Docling을 동시에 띄우면 OOM(exit 137)이 난다 — 7.5GB에서 순차로 돌린다.

### ⑧-2 — 배포용 코퍼스 신규 수집·파싱·색인

> **범위 변경 (2026-08-13)**: 종전 제목은 "재파싱 + 재색인"이었고 대상은 로컬 30,065편이었다.
> 이제 대상은 **신규 수집분**이며, 아래 감사 도구·기준선 작업은 전부 그대로 유효하다
> (같은 파서·같은 감사로 신규 수집분을 잰다). 배치 절차에서만 다음이 달라진다:
>
> | 항목 | 재파싱 전제였을 때 | 신규 수집에서는 |
> |---|---|---|
> | 저장된 앵커 무효화 | 필수 — 블록 id 재할당이 기존 u7 요약·evidence 앵커를 오귀속시킴 | **발생 안 함** — 기존 논문을 다시 파싱하지 않으므로 무효화할 캐시가 없다 |

> **신규로 생기는 선행 작업**: 기반 논문 목록 수집(날짜 창으로는 안 들어옴 — 실측) ·
> S2/OpenAlex 적재 전 분야 필터 · 저널 품질 하한. 근거는 질문지 Q3·Q4.

**착수 전 선행 작업: 감사 도구를 자산 단계까지 내린다.** ⑧-1.10의 패널 크롭 결함이 유형별
스윕에 안 잡힌 것을 계기로 도구 7종을 점검한 결과, **자산을 렌더하거나 세는 도구가 하나도
없다** — 전부 doc-model에서 멈추고, `table_repair_audit`만 파서 너머로 가되 표 행만 본다.
독자가 실제로 보는 이미지 층 전체가 자동 측정 사각지대다. 3만 편을 재파싱하는 배치가 이
숫자들을 스스로 보고하게 만드는 것이 가장 값이 크므로, 배치 착수 전에 붙인다.

빠진 것을 "독자에게 조용히 잘못 보이는가" 순으로:

1. **참조는 있는데 이미지가 없다.** `figure_missing_assetref`는 블록에 참조가 달렸는지만 본다.
   그 참조가 가리키는 이미지가 저장됐는지는 아무도 안 본다 — 화면에는 placeholder가 뜬다.
   ⑧-1.10 실측: 2409.08036 **15/149**, 2608.07458 **5/24**, OpenAlex 편 **2/41**.
   여기에 이번 브랜치가 새 문제를 얹었다: **캡션-전용 거부는 이제 의도된 동작**인데, 지금
   도구로는 "설계대로 거부"와 "조용히 잃음"을 구분할 수 없다. 배치에서 둘이 섞이면 어느 쪽이
   몇 건인지 영영 모른다. 거부 로그(⑧-1.9)는 반쪽이고 나머지 반쪽이 이것이다.
2. **크롭 사각형.** 슬라이버(⑧-1.10)와 그 반대 방향(옆 표·이웃 문단을 삼킨 크롭) 둘 다
   보이지 않는다. 판정 신호는 실측으로 확인됐다 — `포착 높이 / 캡션 위 연속 그래픽 덩어리`가
   결함 0.20 대 정상 1.00으로 깔끔히 갈린다. 여기에 크롭끼리의 겹침 검사를 더한다.
3. **가짜 float가 잃은 float를 가린다.** `lost_figures`는 개수 뺄셈이라, GROBID가 본문 문단을
   그림/표로 만들면 블록 수가 올라가 손실이 상쇄된다(⑧-1.10에서 `'-P peaks at d = 2'`,
   `'K'`, `'?'` 라벨로 실제 관측). 집합 비교(`unmatched_figures`)를 위반으로 올리는 것은
   답이 아니다 — 라벨이 깨져 3개 있는 표를 6개 유실로 오보한 측정 근거가 docstring에 있다.
   대신 **번호를 못 읽는 라벨을 가진 블록 수**를 따로 센다.
4. **붙은 셀이 유형 히스토그램에 없다.** `empty_table`은 행이 0일 때만 잡아, 표 전체가 한 행에
   뭉쳐도 깨끗하게 나온다. 수치는 `table_repair_audit`에 따로 있으니 같은 리포트로 합친다.

1~3은 감사가 크롭 스펙과 저장 결과를 대조하면 한 자리에서 다 나온다.

**완료 (2026-08-12).** 두 부분으로 붙였다. 프로덕션은 `crop_assets_from_specs`가 거부 사유를
모으고(`page_missing`/`not_renderable`/`caption_only`/`render_failed`) `ingestion.assets.refused
{reason}`로 방출한다 — 배치가 자기 placeholder 비율을 원인별로 보고한다. 감사는 `_assets.py`가
크롭을 실제로 렌더해 판정하고, 위반 유형 4종(`crop_missing`·`crop_duplicate`·
`table_cells_merged`·`float_label_unreadable`)이 추가됐다.

넓게 패딩된 경우도 걸린다(2504.00366: 완전한 크롭이 0.62). 기준선에서 틀리는 위반 유형은
히스토그램 전체를 무시하게 만들므로 런 간 비교용 신호로 남겼다.

### ⑧-1.11 — 4경로 실스택 눈확인 (2026-08-12)

이번 수리는 PDF 크롭 단계만 건드리지만, 배치 직전이므로 논문이 코퍼스로 들어오는 **네 경로
전부**를 최종 코드로 돌려 화면까지 확인했다. 이번에는 `~/data/docsuri-data`에 직접 넣었다 —
표본이 코퍼스에서 뽑힌 논문들이고 ⑧-2가 어차피 전부 다시 쓰므로 덮어쓴 3편은 배치가 할 일을
며칠 앞당긴 것에 불과하다(백업은 `~/data/docsuri-verify/corpus-backup/`에 남겼다). 별도 폴더로
하면 계정·세션이 갈려 `./dev.sh`가 그대로 안 먹는 실무 비용이 더 컸다.

| arXiv → PDF → GROBID | 2505.18502 | `no_figure_evidence` 1건 — 이번 수리가 실동작 |

**`%PDF-` 가드가 실트래픽에서 도는 것을 봤다** — S2 수확 60건 중 13건이 비-PDF로 걸렸다
(2.7KB 랜딩 페이지, 474KB HTML). 가드가 없었으면 그 HTML이 GROBID로 가서 500 → 재시도 → DLQ
코스였다.

**S2 도달률을 오판할 뻔했다.** 60건 중 45건이 출판사 403(MDPI·ScienceDirect), 13건이 비-PDF,
**24건은 GROBID가 OOM으로 죽어 있어서**였다. 마지막 항목을 S2 실패로 셌으면 도달률을 크게
과소평가했을 것이다. GROBID를 되살리자 첫 시도에 성공했다. ⑧-1.10의 운영 메모(GROBID·Docling
동시 기동 금지)를 어겨서 생긴 일이고, ⑧-2 배치는 두 단계를 반드시 순차로 돌려야 한다.

**화면에서 나온 지적 두 건의 판정.** 그림이 뭉개져 보인 건 **원본 PDF 문제**다 — 그 그림은 PDF
안에 491x238px(96 DPI) 래스터로 박혀 있고 우리는 2배로 렌더해 737x357px로 저장했다(원본보다
크다). 같은 논문의 다른 그림이 선명한 것이 근거다(벡터라 배율만큼 선명해진다). 배율을 올려도
뭉개짐은 그대로고 용량만 는다. S2/OpenAlex 논문에 arXiv 링크가 걸린 건 **검증 스크립트
결함**이었다 — 실제 파이프라인은 `ParsedPaper.source_name`/`source_url`을 채우는데
(`application.py`) 급조한 색인 헬퍼가 빠뜨려 `source_ref`가 arXiv 기본값으로 떨어졌다.
제품 수정 없음, 스크립트만 고쳐 재색인했다.

**뷰어는 URL의 버전으로 아티팩트를 찾는다**(`frontend/lib/arxivVersion.ts`). `/paper/2505.18502`는
v1을 요청하므로 doc-model이 v3인 논문은 "원문을 가져올 수 없다"가 뜬다. 눈확인 URL에는 항상
버전을 붙여야 한다 — `/paper/2505.18502v3/doc-model`.

- **arXiv 경로 사다리는 ⑧-1.5에서 재확정** — `ar5iv HTML(품질검사) → arXiv PDF → GROBID`.
  native HTML 단은 제거됐다. 재파싱 시간 산정에는 품질검사 탈락·ar5iv 부재분이 GROBID로
  내려가는 비중(최신 논문일수록 큼)을 반영해야 한다.

  영어 논문 검색)가 필요하고 `shared/vector-spec`도 Cohere로 FROZEN이라 원 설계와 정합이다.
  `cohere.embed-v4:0`, $0.12/1M 토큰. 온디맨드가 us-east-1 / eu-west-1 / ap-northeast-1뿐이라
  **서울에 없어** 임베딩만 교차 리전으로 부른다. 로컬 실측 편당 85KB ≈ 21.7K 토큰 기준
  4,500편이면 **약 $14**.
  **색인과 검색이 같은 모델을 써야 한다** — 둘 다 1024차원이라 차원 검사로는 못 잡고, 증상이
  "검색 품질이 나쁘다"로만 나타난다. 실제로 수집이 `DOCSURI_EMBEDDING_PROVIDER`를 무시하고
  Bedrock으로 하드코딩돼 있어 갈라질 수 있는 상태였다(`bd9eb70`에서 수리).
- **제약은 색인 메모리인데, 그 계산의 전제가 틀려 있었다 (2026-08-14 정정)**

**배치 런북에 선행 점검을 넣는다.** 착수 직전에 셋을 확인하고, 실패하면 배치를 시작하지 않는다:

| # | 점검 | 안 하면 |
|---|---|---|
| 1 | GROBID `/api/isalive` 200 | PDF 경로 42%가 `DEPENDENCY_UNAVAILABLE`로 전멸 |
| 2 | Bedrock 임베딩 1건 왕복(1024차원 확인) | 파싱은 되고 색인만 비는 상태로 몇 시간 |
| 3 | `DOCSURI_CONTROL_PLANE_DSN`·`DOCSURI_OPENSEARCH_INDEX`·`DOCSURI_S3_MIRROR`가 배포 쪽인지 | 개발 코퍼스를 덮어씀 |

세 항목의 공통점은 **실패가 산출물이 아니라 카운터로만 드러난다**는 것이다. 배치 중에도 같은
이유로 주기 점검이 필요하다 — 쿼터는 도중에 소진되고 GROBID는 도중에 죽는다.

재개는 레저 + `--retry-failed`로 실패분만 다시 돈다. 원본 캐시가 있어 재수확 비용은 없다.

후보(Strands는 루프 중간 저장이 없고, Pydantic AI는 엔진이 하나 더 필요). 비교표·지킬 규칙은

## ⑩-1 evidence

### 목적 (2026-08-20 확정)

> **evidence는 문헌에 근거해 답하는 챗봇이다.**
> 사용자가 던진 주장이나 질문에 대해, 논문을 찾아 읽고, 인용을 달아, **판단까지 포함한
> 답변**을 한다. 근거를 못 찾으면 답을 지어내지 않고 못 찾았다고 말한다.

목적이 정해진 적이 없었다 — `solo-agent/requirement-verification-questions-evidence-agent-v2.md`
15문항은 전부 "어떻게 만드나"(인용 대상 블록·계약 필드·모듈 경계·URL)이고, 상속받은
"검색 전략만 자율"은 목적이 아니라 **자율성의 범위**다. novelty 쪽은 ④에서 이미 정해져
있다(기능 정의 Q1=X·Q3=X·Q4=B). 그 공백이 실제 어긋남으로 남았다.

**1. 판단은 조건부로 한다.** 문헌이 갈리면 갈린 채로 보여주되, **무엇이 가르는지**를 밝힌다.
종합해서 한쪽으로 단정하지 않는다 — 근거로 검증할 수 없는 문장이 들어가기 때문이다.

```
Q. LoRA가 전체 파인튜닝보다 좋아?
A. 데이터가 적고 도메인이 사전학습과 가까울 때는 LoRA가 비슷하거나 더 나은 성능을
   냅니다(A, B). 반면 도메인이 크게 다르거나 학습량이 클 때는 전체 파인튜닝이
   앞섭니다(C). 갈리는 지점은 '적응 과제가 사전학습 분포 안에 있느냐'입니다.
```

**2. 못 찾으면 부분 답 + 다음 행동을 준다.** 찾은 만큼은 답하고 어디까지 확인했는지를
밝힌다. 전혀 없으면 없다고 말하되 **왜** 없는지(코퍼스 밖 / 근거 부족)와 다음 수를 준다.

```
[부분]  …반대 조건을 다룬 논문은 확인된 범위에서 못 찾았습니다 — 후보 24편 중
        8편까지 봤고 예산으로 멈췄습니다. → 이어서 더 찾기
[없음]  이 주제를 다룬 논문을 코퍼스에서 못 찾았습니다. arXiv에서 수집해볼까요?
```

**3. 대화 안에서 끝난다.** 침묵 금지(진행이 보인다) · 언제든 취소 · 취소해도 부분 결과.
시간 상한은 목적이 아니라 안전 밸브다.

### PR 2 — 실행 경로 통합 (2026-08-24, `feature/evidence-turn-execution`)

진입 경로 셋(동기 JSON / 동기 SSE / SQS+폴링)을 **수락(202) → 이벤트 SSE → 취소 → 폴링** 하나로
합쳤다. 실행자는 SQS 워커 또는 프로세스 내 스레드풀이고 둘 다 `process_job` 하나를 돈다.
그래프 채널을 순수 JSON으로 바꿔 Postgres saver가 super-step마다 스냅샷을 쓰고(`thread_id=
turn_id`), 실행자가 죽은 턴은 하트비트 끊김을 보고 마지막 스냅샷으로 부분 답을 만든다.
취소는 novelty와 같은 행 플래그 + `decide` 경계 확인. 세션당 pending 하나는 부분 유니크
인덱스. FE는 수락 뒤 `activeTurnId` 구독 effect가 답변을 받고, 진행 중엔 취소 버튼이 선다.
잡힌 것 — 트레이스 행이 flush만 되고 잡이 끝나야 커밋돼 이벤트 스트림이 완료 때까지 빈
채였던 것(실행자를 짧은 트랜잭션으로, 실 Postgres 게이트 테스트를 CI에), 완료된 thread는
재invoke해도 아예 안 도는 것(비우지 않으면 재배달 잡이 무동작으로 성공한다), 실행자 재수화
페이로드에 첨부 id가 없어 신원 검증이 항상 실패하던 것, novelty FE가 치는 `/events` 라우트가
백엔드에 없던 것.

정리 패스에서 더 잡힌 것 셋 — ① 체크포인트 조작을 러너에 매달아 세션 삭제·취소·이벤트 등
5개 라우트가 LLM 러너 의존이 되면서 **러너 미구성 배포에서 세션 삭제가 500**이었다(→
`TurnCheckpoints`로 분리). ② 정리 질의에 도장이 없어 같은 앞쪽 200건을 영원히 재삭제하고
그 뒤 턴은 영영 안 지워졌다 — 로그는 `pruned: 200`으로 정상이었다(→ `checkpoints_pruned_at`).
③ `first_token_ms`를 접속 직후에 방출해 구조적으로 0이었다(→ 첫 tool 프레임에서).
넷째는 그 자리에서 겪었다 — 러너 빌더 인자 이름을 안 맞춰 evidence 마운트가 실패했는데
앱은 초록으로 떴고 evidence만 `skipped`였다. 서명 드리프트 가드를 붙였다.

실측: 7도구 턴 체크포인트 16건·**59.7 kB**(스냅샷 다이어트 전 9도구 턴은 22건·493 kB),
취소 후 부분 답, 겹침 409, SIGKILL 고아 턴을 근거 4건의 부분 답으로 마감, SIGTERM 2초 내
종료, 세션 삭제 시 체크포인트 0. 백엔드 595 passed(PG 게이트 5건 포함)·프론트 323 passed.
세부는 설계 §3.1·§5 "PR 2 실행 결과".

### PR 3 — 판단 층 (2026-08-24, `feature/evidence-judgment`)

`answer` 노드를 얹어 게이트 통과 근거만 보고 **산문 판단**을 쓰게 했다. 근거가 있으면 모든
종료 경로(충분·예산·취소·치명 오류·중단)가 이 노드를 지난다. 검사 5종(A1~A5)은 전부 문자열·
집합 연산이고 LLM-judge를 쓰지 않는다 — 강등 2종은 문장이 남되 표시를 잃고, 거부 3종은
재생성 1회 뒤 결정론 이어붙이기로 떨어진다(C-2 fail-closed).

잡힌 것 — **첫 실행은 판단이 전부 사라진 채였다**(`fallback_rate=1.0`). 모델이 맨 JSON 배열로
답하는데 파서가 못 읽어 문장 0건 → A4 거부 → 재생성 → 폴백으로 흘렀고, 예외도 로그도 없었다.
골든셋이 없었으면 "판단 없는 답"이 그대로 나갔다. 같이 고친 것: `_act`가 **도구별 상한**을 전역
예산 소진과 똑같이 취급해 턴을 끝내고 있었다 — `fetch_paper` 3/3에 막힌 턴이 논문 3편·256블록을
쥔 채 추출을 한 번도 안 부르고 기권했다(`cap_fetch_paper` 3 → 8). 정리 패스에서 더 잡힌 것:
프론트 타입 드리프트 가드가 **구조적으로 실패할 수 없었고**(무시되는 경로만 비교했다), 지표를
재는 `summarise`가 평균을 진리값으로 걸러 0.0인 문항을 빼고 있었다(0.232로 보고, 실제 0.193).

### PR 4 — 탐색 (2026-08-25, `feature/evidence-exploration`)

연도 제약(`year_from`/`to`, U2 포트까지 push-down) · 실시간 조회 세 소스(`live_lookup`) ·
반대 측 탐색 바닥 조건(`stance`) · 턴 이어가기와 세션 기억 · 백그라운드 색인 · 골든셋 51문항.

**실스택이 목으로는 못 잡는 것을 잡았다.** ① S2는 무키로 사실상 항상 429다(12초 간격 5회 연속) —
그런데도 매 턴 부르면 왕복을 버리고 화면에 "실시간 조회 불가"가 **상시로** 뜬다. 미구성을 장애로
보여주면 진짜 장애가 묻히므로 키가 있을 때만 합류하게 했다. ② `live_lookup`이 arXiv 밖 논문을
`doi:`로 실어 오는데 `fetch_paper`가 그것을 승격 큐로 보내 20초 폴링을 태우고 있었다 — 결과는
"초록 범위로 계속"으로 같아 **로그만 봐서는 정상**이다.

**설계가 틀렸던 것 셋을 정정했다.** `delete_thread`는 `thread_id=turn_id`라 현재 턴만 지우므로
걷어낼 필요가 없었고(§5.5의 좁은 창은 그대로 남는다), ingestion 클라이언트 재사용은 저쪽에
질의 검색이 없어 성립하지 않았으며, 이어가기의 `continuation` 선언은 놓을 자리가 없었다
(이식이 루프보다 먼저다).

**승격만으로는 코퍼스가 자라지 않았다.** `BUILD_DOC_MODEL`은 본문만 만들고 U1의 그 핸들러
docstring이 "이 잡은 **이미 색인된** 논문을 위한 것"이라고 적어 뒀다 — `EVENT` 잡을 본 큐에
넣어 색인까지 태운다. 실 SQS 전송과 **U1 파서가 그 페이로드를 실제로 파싱**하는 것까지 확인했다.

**검수 게이트를 빨간 빌드에서 구조로 옮겼다.** 종전 규칙은 문항을 늘릴 때마다 CI를 빨갛게 만들
뿐 미검수 라벨로 점수를 재는 것 자체는 막지 못했다(빨간 채로 점수는 그대로 나왔다). 이제 채점
경로가 미검수를 안 받는다.

실측: 1층 51문항 위반 0(녹화 픽스처 — 대본이 기대대로 도니 recall@k는 구조적으로 1.00이다).
레인 shared 113 · discovery 159 · backend 780 · frontend 331. 커밋 7개 각각 단독 통과.
**2층은 16문항 중 3건만 유효하다** — 4번째부터 13건이 Bedrock 스로틀로 죽었고, 돈 3건은 판정
9개 전부 pass다. 쿼터가 눌린 상태라 조용한 창에서 다시 돈다. 세부는 설계 §3.2·§3.3·§3.4·§10.

**4번이 이번 작업의 중심이다.** 지금은 답변 문장 전체가 인용문 조합이라 C-2가 자동으로
지켜졌다. 판단 문장이 들어오면 **검증되는 부분(인용·수치)과 검증되지 않는 부분(조건 구분·
갈림 지점 서술)이 한 답변에 섞인다.** 무엇을 기계가 잡고 무엇을 못 잡는지를 계약에 드러내야
한다 — `sourceScope`가 근거 범위 등급을 출처 단위로 싣는 방식(Q3=B)과 같은 결이다.

**딸려 오는 것**: `assemble()`의 결정론 전제가 깨진다("같은 입력이면 같은 출력"). 회귀
픽스처·PBT를 판단 문장을 포함하지 않는 부분(claims·coverage)에 한정하도록 다시 짠다.

**살아 있는 자산**: `EvidenceCoverage`가 이미 `examined`·`candidates`·`stoppedReason`을
싣고 있어 2번의 "후보 24편 중 8편까지" 문장을 만들 재료가 있다. 새로 만들 것은 표현 경로다.

### 중간 취소 (구 ⑨-2) — PR 2에서 완료

evidence에는 스티어링도 취소도 없었다(novelty에만 있다). **취소만 넣었다.**

턴이 짧아(수초~30초) 방향 전환은 다음 턴에 말하면 되므로 스티어링의 값이 작은 반면,
메시지 저장·주입 시점·경합 처리가 전부 딸려온다. 반면 취소는 길이와 무관하게 필요하다 —
탐색이 길어질 때 사용자가 비용을 멈출 수단이 있어야 한다. novelty의 협조적 취소(BR-RA8:
진행 중 도구 호출 완료 후 턴 경계에서 탈출)와 같은 방식으로 맞춘다.

### ⑧-2 마감 판정 (2026-08-25)

**3,248편으로 마감한다.** 실측은 배포 색인 `docsuri-deploy-v1`의 고유 `paperId` 집계다.

근거는 편수가 아니라 **천장**이다. 8 GB 박스의 편수 천장이 **약 3,500편**이므로(편당 1.73 MB
실측) 3,248편은 **천장의 93%**다. 더 넣을 자리가 사실상 없다 — 마감은 선택이 아니라 상태다.

**이 판정을 처음에 4 GB·4,500편 기준으로 썼다가 고쳤다**(2026-08-25). §12가 2026-08-15 개정을
안 받아 폐기된 수치를 들고 있었고, 그것을 읽고 "천장 안에 여유롭게 들어간다"로 적었다. 결론은
같지만 근거가 정반대였다 — 여유가 있어서 마감하는 것이 아니라 **꽉 차서** 마감하는 것이다.
정본은 질문지 Q1이고 §12·`requirements.md`·이 문서의 ⑧-2 표까지 함께 고쳤다.

**더 모으는 쪽을 택하지 않은 이유**: ⑧-2 1차 실행이 드러낸 제약이 편수가 아니라 **Bedrock
일일 토큰 한도**(약 800만/일)다. 편당 21.7K 토큰이므로 하루에 넣을 수 있는 편수가 정해져 있고,
그 토큰은 **2층 심판·데모 트래픽과 같은 한도를 나눠 쓴다.** 코퍼스를 더 키우는 것은 배포를
미루면서 배포 후에 쓸 예산을 미리 태우는 선택이다.

**남기는 것**: 재수집은 배포 **후** 별건이다. 원본 캐시가 있어 재수확 비용이 0이므로 언제든
`--retry-failed`로 재개할 수 있다(단 GROBID를 올려야 하고 임베딩 토큰을 다시 쓴다).

**닫지 않은 질문 하나** — **임의 질문의 코퍼스 밖 비율은 아직 안 쟀다.** 골든셋 51문항은
이 코퍼스에서 초록을 읽고 고른 것이라 "이 코퍼스로 답이 되는 질문이 실재한다"의 증거이지
**커버리지의 증거가 아니다.** 배포 후 실제 질문으로 재는 것이 맞다 — 그 전에 재면 표본이
우리가 지어낸 질문이다.

## ⑪ 한시 배포 — Lightsail 단일 인스턴스 (2026-08-25 단계 추가)

결정 자체는 **2026-08-13에 끝나 있었다**(`requirement-verification-questions-corpus-and-deployment.md`
Q1~Q9 · `requirements.md` 개정 블록 · `infrastructure-design.md` §12). 없던 것은 결정이 아니라
**그것을 밟는 자리**다 — 로드맵에 단계가 없어서 "배포를 위해 무엇이 남았는가"에 답할 목록이
어디에도 없었다. 그 공백은 조용히 나쁘다: `ops/cdk/`를 고치는 것이 배포 준비처럼 읽히는데,
§12.5는 그쪽을 **"보존하며 이번 배포에 사용하지 않는다"**고 이미 정해 놨다.

### 확정된 것 (다시 정하지 않는다)

| 항목 | 값 | 근거 |
|---|---|---|
| 인스턴스 | Lightsail `large_3_0` — **8 GB** · 2 vCPU · SSD 160 GB | 질문지 Q1=C (2026-08-15 개정) |
| 비용 | $44/월 × 3개월 = **$144** (개인 계정 프리티어 크레딧) | 질문지 Q1=C |
| 계정 | puppytalk과 공유 — 무료 번들(2 GB)은 puppytalk | §12.1 |
| 구성 | 로컬 `docker compose`를 그대로 이관 + Caddy(TLS) | §12.2 |
| 편수 천장 | **약 3,500편** (8 GB · **편당 1.73 MB 실측** · 완화책 미적용) | 질문지 Q1=C |
| 파싱 스택 | **배포 박스에 올리지 않는다** — 색인 결과만 올린다 | §12.4 (Q7=B) |

### 이 단계가 실제로 해야 하는 것

1. **배포 자산이 저장소에 없다.** Terraform도, 배포용 compose도, 런북도 0건이다. §12.4가
   선례로 지목한 `puppytalk-infra/demo/`는 **다른 저장소**다. 인스턴스 생성·고정 IP·방화벽·
   Caddy·이미지 빌드·SSH 배포가 전부 남아 있다.
2. **색인·코퍼스 이관** — 파싱 스택을 안 올리므로 로컬에서 만든 색인과 doc-model을 박스로
   옮긴다. 오브젝트 스토어는 s3proxy가 아니라 **실 S3**로 갈린다(§12.2).
3. **배포본 동작 확인** — 로컬 `./dev.sh`가 도는 것과 배포본이 도는 것은 다른 명제다.
   ⑧-2 1차 실행이 남긴 교훈이 그대로 적용된다: **실패가 산출물이 아니라 카운터로만 드러난다.**

### 배포에서 갈리는 동작 — 미리 적어 둔다

한시 토폴로지는 로컬·실서비스와 **의도적으로** 다르고, 그 차이가 에이전트 동작으로 새어 나온다.
배포 후에 "왜 안 되지"로 만나지 않도록 여기에 적는다.

- **실시간 조회는 기본 off다**(`DOCSURI_EVIDENCE_LIVE_LOOKUP_ENABLED`). 배포 코퍼스가
  실서비스보다 훨씬 얇으므로 **켜는 쪽이 기본값이 되어야 하는 자리**인데, 켜는 것은 결정이라
  코드가 정하지 않는다. 조회는 외부 API 호출뿐이라 파싱 스택이 없어도 돈다.
- **본문 승격은 배포 박스에서 돌지 않는다.** 승격은 `BUILD_DOC_MODEL` 잡을 큐에 넣고 워커가
  받아야 하는데, 한시 토폴로지에는 SQS도 그 워커도 없다(§12.2에서 큐는 Redis로 대체된다).
  즉 **코퍼스 밖 논문은 초록까지만** 답에 쓰인다 — 설계가 이미 그 경계를 정해 뒀고(초록 범위
  인용 게이트), 배포에서는 그것이 예외가 아니라 상시 상태가 된다.
- **Novelty 모드는 내보내지 않는다**(2026-08-25 결정). ⑩-2 재정의를 하지 않기로 했으므로
  지금 노출되는 것은 그 재정의 **이전**의 v2다 — 임무가 모호한 채로 데모에 서면 evidence가
  받아야 할 평가까지 흐려진다. 코드는 그대로 두고 **진입점만** 가린다
  (`NEXT_PUBLIC_DOCSURI_NOVELTY_ENABLED`, 기본 미노출). 되돌리는 데 env 하나면 된다.
- **백그라운드 색인은 꺼진다.** §2.6 4단계는 U1 본 큐에 `EVENT` 잡을 넣는데, 배포에는 그
  큐도 파싱 스택도 없다. `DOCSURI_SQS_QUEUE_URL`이 없으면 색인만 조용히 꺼지도록 만들어 뒀고,
  이것은 결함이 아니라 **Q7=B("배포 기간 중 증분 수집 없음")와 정합**이다. 그래서 "쓸수록
  코퍼스가 자란다"는 배포본에서 성립하지 않는다.

### 선행 점검 (⑧-2에서 두 번 데인 것)

배포 직전·직후에 확인한다. 셋 다 **실패가 화면에 안 보이는** 종류다.

| # | 점검 | 안 하면 |
|---|---|---|
| 1 | 박스의 `DOCSURI_S3_MIRROR`/버킷이 배포 쪽인지 | 개발 코퍼스를 덮어쓰거나, 전문이 백지로 뜬다 |
| 2 | OpenSearch가 실제 편수를 들고 떴는지(`_cat/indices`) | 검색이 조용히 적게 나오고 "논문이 드물다"로 읽힌다 |
| 3 | Bedrock 자격증명·리전·일일 토큰 여유 | 답변이 `llm_unavailable`로 기권하고 로그만 조용하다 |
| 4 | `NEXT_PUBLIC_DOCSURI_NOVELTY_ENABLED`가 **안** 켜졌는지 | Novelty 모드가 데모에 노출된다 — 빌드 시점에 박히므로 배포 후에는 재빌드해야 고친다 |
