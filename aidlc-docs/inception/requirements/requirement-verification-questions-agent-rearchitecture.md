# 에이전트 아키텍처 재설계 — 요구사항 명확화 질문 (Agent Re-architecture)

**단계**: INCEPTION → Requirements Analysis (솔로 유지보수 사이클)
**일자**: 2026-07-17
**상태**: ✅ 확정 (2026-07-18)
**결정 요약**: 최종형은 supervisor–서브 에이전트 구조(Q1=C). novelty 단일 루프부터 착수(Q3=A), 모듈 내부 재작성(Q4=A), 단일 루프는 직접 구현하고 supervisor 단계에서 LangGraph 도입(Q5=A). API·화면 계약은 유지(Q6=A)였다가 **기능 정의 확정(2026-07-18, `requirement-verification-questions-novelty-v2-function.md` Q7=B)으로 B(새 산출물에 맞춘 재설계 허용)로 개정** — 결정 트레이스 서버 저장 조건은 유지. requirements는 소규모 델타 개정(Q7=A, 기능 정의 개정 포함), 이번 사이클은 설계 문서까지(Q8=A).
**대상**: 문헌탐색·근거형성(U11, `backend/modules/{evidence,research}/`)과 연구 아이디어(U12, `backend/modules/novelty/`) 두 기능의 에이전트 아키텍처 전면 재검토.
**목적**: 에이전트 개발 역량(Tool Calling·Planning·Memory·MCP·멀티 에이전트)을 실제 동작하는 시스템으로 완성. 배포는 비용 확보 전까지 로컬 완성 우선.
**결정 방식**: 각 질문의 `[Answer]:`에 선택지 문자를 기입. 이 질문지의 답이 확정되면 → ① `solo-roadmap.md` 개정, ② 기존 유닛 질문지(`construction/plans/novelty-agent-v2-functional-design-plan.md`) 답 상속·갱신, ③ 유닛 설계 문서 작성 순으로 기계적으로 진행한다.

## 전제 (현황)

- **문헌탐색·근거형성**: 기계식 파이프라인(검색→추출→비교표)으로 **현재 정상 동작**. novelty와 채팅 화면이 이 엔진에 의존. 날조 금지(C-2)의 신뢰 코어.
- **novelty**: 고정 상태머신(QUEUED→…→EXPORTING_NOTION). 어떤 주제든 같은 순서로만 동작 — 재설계 필요성의 진원지.
- 플랫폼 기능(U2 검색·DocModel·요약·figure crop·비용 가드)은 두 모듈 밖에 있어 **어떤 선택을 해도 재사용**된다.

## Q1 — 최종 목표 구조

이 프로젝트의 에이전트 최종형을 무엇으로 하는가? (이 답이 나머지 질문의 기준점)

- **A) 단일 에이전트** — 연구 에이전트 1개(자율 루프)만 만들고, 문헌탐색은 그 도구이자 별도 채팅(기계식)으로 유지. *가장 작고 완성 확실 / 멀티 에이전트 경험 없음.*
- **B) 독립 에이전트 2개** — 연구 에이전트 + 문헌탐색 에이전트를 각자 화면 뒤에 독립적으로 두고, supervisor 없음. *둘 다 에이전트화 경험 / 에이전트 간 협업·배선 경험은 없음.*
- **C) supervisor 완성형** — supervisor(연구 오케스트레이터)가 서브 에이전트들(문헌탐색 탐색 워커, 아이디어 생성)을 지휘·병렬 실행하는 멀티 에이전트 시스템까지 완주. *Tool Calling·Planning·Memory·MCP·멀티 에이전트 전부 커버 / 작업량 최대, 중간 단계마다 동작 가능 상태 유지 필요.* (권장)
- **X) 기타**

[Answer]: C

## Q2 — 문헌탐색 에이전트화의 자율 범위

문헌탐색을 에이전트로 만들 때(Q1=B/C) 자율을 어디까지 주는가?

- **A) 검색 전략만 자율** — "어떤 검색어로, 어떤 논문을 깊이 읽고, 언제 충분한지"는 LLM이 판단. 문장 추출·근거표 조립·날조 검사 게이트는 기계식 유지. *탐색 품질 개선 + 날조 위험 0 유지. 업계 표준 패턴(deep research의 탐색 워커).* (권장)
- **B) 전 과정 자율** — 추출·조립까지 LLM 재량. *유연성 최대 / 날조 금지(C-2) 보증 상실 — 근거 기능의 존재 이유와 충돌 → 사실상 기각 후보.*
- **X) 기타**

[Answer]: A

## Q3 — 착수 순서

어느 모듈부터 에이전트화하는가?

- **A) novelty 먼저** — novelty는 의존받는 게 없는 말단이라 실험 실패 비용이 낮고, 문헌탐색(신뢰 코어·피의존)은 루프 구현 경험을 쌓은 뒤 건드린다. 현재 novelty가 기계식 문헌탐색 엔진을 호출하는 의존은 그대로 충족된다. (권장)
- **B) 문헌탐색 먼저** — 의존 부품(서브 에이전트가 될 것)부터 상향식으로. *supervisor 단계의 부품이 먼저 준비됨 / 잘 돌아가는 신뢰 코어와 그 피의존(novelty·채팅)을 첫 실험 대상으로 삼는 리스크.*
- **X) 기타**

[Answer]: A

## Q4 — 코드 전략

두 모듈의 기존 코드를 어떻게 다루는가? (플랫폼 기능·공유 계약(DTO/포트)은 어느 쪽이든 유지)

- **A) 모듈 내부 재작성** — 에이전트 모듈을 새로 짜고, 기존 모듈에서 가치 있는 부품(추출 로직·검증·저장)만 이식. 구조가 근본적으로 달라지므로(파이프라인→루프) 개조보다 깨끗함. *과도기에 신구 병존 관리 필요.*
- **B) 점진 개조** — 기존 모듈 위에 루프를 이식하며 단계적으로 교체. *항상 동작 상태 유지 / 파이프라인 잔재가 설계를 오염시킬 위험.*
- **X) 기타**

[Answer]: A

## Q5 — 프레임워크 전략

에이전트 루프와 멀티 에이전트 배선을 무엇으로 구현하는가?

- **A) 단일 루프는 직접 구현 → supervisor 단계에서 LangGraph 도입** — 단일 에이전트 루프는 외부 의존 없이 직접 구현하고, 병렬 서브 에이전트 실행·에이전트 간 상태 전달이 실제로 필요해지는 supervisor 단계에서 LangGraph를 도입. *단일 루프는 무의존·단순 유지 / 멀티 에이전트 배선(병렬 실행, 상태 전달, 체크포인트)은 검증된 프레임워크로 처리.* (권장)
- **B) 처음부터 LangGraph** — 전 단계를 LangGraph로. *초기부터 도구 체계 일관 / 단일 루프에는 과한 의존성, 프레임워크 추상에 가려 루프 동작 파악이 어려워질 위험.*
- **C) 끝까지 직접 구현** — LangGraph 미사용. *외부 의존 0 / 병렬 실행·상태 전달·재시도·체크포인트를 전부 수작업으로 구현·유지해야 함.*
- **X) 기타**

[Answer]: A

## Q6 — 기존 API·화면 계약

FE 채팅 화면과 REST 계약(진행상태 enum 포함)을 유지하는가?

- **A) 유지** — 화면 무변경, 루프의 활동을 기존 진행상태 enum으로 투영. *FE 작업 0 / 도구 호출 단위의 세밀한 진행 표시는 제한.* (권장)
- **B) 계약 재설계 허용** — 에이전트에 맞는 새 이벤트 계약 + FE 갱신. *진행 표시 표현력↑ / FE 작업 동반, 완성까지의 거리 증가.*
- **X) 기타**

[Answer]: A — 조건: REST 계약은 유지하되, 에이전트의 결정 트레이스(선택한 도구·질의·종료 사유)는 루프 도입 시점부터 서버에 구조화 저장한다. 자율 루프 디버깅·근거 재현성에 필수이며 소급 수집이 불가능하기 때문. FE 노출은 별도 결정.
  *(2026-07-18 개정: 기능 정의 질문지 `requirement-verification-questions-novelty-v2-function.md` Q7=B 확정에 따라 본 답을 **A → B(계약 재설계 허용)**로 개정 — 기능 정의(여백 분석 신설·실험 계획 온디맨드화·위험 신호 폐기·대화 스티어링)가 달라진 만큼 결과 렌더링·잡 API 계약을 새 산출물에 맞춘다. 채팅 화면·모드 구조와 결정 트레이스 저장 조건은 유지.)*

## Q7 — 요구사항 문서 처리

`requirements.md`(FR-30~35 등)를 어떻게 갱신하는가?

- **A) 소규모 개정 블록** — 기존 FR 유지 + 델타만 개정(외부 탐색 메커니즘 중립화, 세션 메모리 신규 FR, 진행상태 enum 재해석 각주). 기존 개정 관례(2026-06-29 블록)와 동일 형식. (권장)
- **B) 재인셉션 수준 전면 개정** — 에이전트 장을 새로 씀. *엄밀 / 문서 작업량이 구현 시간을 잠식.*
- **X) 기타**

[Answer]: A — 델타는 5건으로 확장: ① 외부 탐색 메커니즘 중립화(Agent-Browser → 외부 탐색 어댑터, MCP 포함) ② 세션 메모리 신규 FR ③ 진행상태 enum 재해석 각주 ④ 루프 예산·반복 상한 FR(자율 종료 도입에 따른 안전 요건) ⑤ 결정 추적성 FR(Q6 조건의 요구사항 승격).
