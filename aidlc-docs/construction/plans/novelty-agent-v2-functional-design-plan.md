- 코드 전략은 **모듈 내부 재작성** — 기존 파이프라인 위 개조가 아니라 새 루프 코어를 짜고 가치 있는 부품만 이식 (arch Q4=A).

- 이번 사이클 산출물은 설계 문서까지, 구현은 로드맵 ⑤ (arch Q8=A).

**용어**: **루프** = 에이전트가 "상황 보기 → 다음 행동 고르기 → 실행"을 반복하는 구조. **도구** = 루프가 호출할 수 있는 기능 부품(검색, 저장 등 — 스스로 판단하지 않음). **산출물** = 잡이 끝났을 때 남는 결과 데이터(유사 연구 표, 여백 분석 등). **게이트** = 저장·통과 전에 거는 기계식 검사. **MCP** = 외부 서비스(arXiv·GitHub·Notion 등)를 에이전트 도구로 꽂는 표준 연결 규격. **DocModel** = 논문 1편의 구조(섹션·문장 좌표·그림·표·수식 목록)를 담은 우리 쪽 데이터 — 근거 검증과 figure 조회의 원천.

## 1. 유닛 컨텍스트

- **대상**: Novelty Agent v2 — 현행 novelty 모듈(고정 상태머신 QUEUED→…→EXPORTING_NOTION)의 **도구 호출 루프 기반 재설계** 목표 아키텍처.
- **명칭**: 유닛명·코드 경로 모두 **novelty 유지**. "research*" 계열 명칭은 로드맵 ⑦ supervisor 명명 후보로 예약 (`backend/modules/research/`는 문헌탐색·근거형성 Agent(U11)의 대화 표면 — 본 유닛과 무관).
- **책임**(2026-07-18 기능 정의 확정): 자연어 연구 주제 또는 업로드 원고에서 **관련 연구 조사 + 여백 분석**(무엇이 이미 있고 어디가 비어 있는지, 근거 링크 필수)을 기본 산출물로 제공하고, **방향 제안·실험 계획은 대화 요청 시 온디맨드**로 생성한다. 진행상태·선택적 Notion export(승인 게이트) 포함. 원고 위험 신호는 v2 범위에서 폐기.
- **문서 위치**: 설계 문서는 `construction/novelty-agent-v2/`에 둔다 (`construction/novelty-agent/`는 v1 frozen 기준선).
- **범위 경계 (로드맵 ④/⑤)**: 이번 라운드는 **설계 문서만** 산출한다. 코드 재작성(에이전트 루프 → MCP 연동 → 세션 메모리 → 멀티모달)은 로드맵 ⑤ — 본 설계는 그 4단계 도입을 수용할 수 있어야 한다. 모듈 경로는 유지하되, API·화면 계약은 새 산출물 기준으로 재설계한다(기능 정의 Q7=B).
- **v2 제외**: 뉴스 검색, novelty 점수, "새로움 확정" 판정, 논문화 가능성 점수, 코드 skeleton/실행 스크립트 생성(이상 승계), **원고 위험 신호(표절 유사도·AI 어투 — 기능 정의 Q5=B로 폐기)**.

### A. 아키텍처 코어

#### Q1 — 에이전트가 일하는 기본 틀
에이전트가 매 순간 "다음에 뭘 할지"를 어디까지 스스로 정하게 할 것인가. 조사는 "하다 보니 방향이 바뀌는" 일이라, 이 답이 v2의 성격을 결정한다.

- **A) 완전 자율 루프** — 매 턴 "지금까지 알아낸 것"을 보고 다음 도구·질의를 스스로 고르고, 필수 산출물이 다 차거나(Q4) 예산이 소진되면(Q9) 종료. 조사 중 발견("이 여백 후보, 진짜 비었나?")에 즉시 반응해 경로를 바꿀 수 있다. 안전은 저장 게이트(Q8)와 예산(Q9)이 담당하므로 틀을 굳혀서 얻을 안전은 없다. (권장)
- **B) 큰 단계는 고정(조사→분석→보고), 단계 안에서만 자율** — 예측하기 쉬움 / 분석하다 "더 찾아봐야겠다" 싶어도 조사 단계로 못 돌아감 — 버리려던 상태머신의 경직성이 절반 남는다.
- **C) 시작할 때 계획을 다 세우고 그대로 실행만** — 감사하기 쉬움 / 중간 발견에 따라 계획을 바꿀 수 없음(다시 계획해야 함).
- **X) 기타**

[Answer]: A — 완전 자율 루프. 종료 조건 = 필수 산출물 완성(Q4) 또는 예산 소진(Q9), 안전은 Q8 게이트·Q9 예산이 담당.

#### Q2 — 진행 상황을 사용자에게 어떻게 보여줄까
현행 화면은 코드에 고정된 **진행상태 목록(enum)** — `queued(대기)→retrieving_corpus(코퍼스 검색)→…→exporting_notion` — 을 타임라인으로 보여준다. 자율 루프는 이 고정 순서대로 돌지 않고, 기능 정의도 바뀌어(여백 분석 신설 등) 옛 이름들이 더는 실제와 안 맞는다. 새 진행 표시 계약을 어떻게 할까. *(계약 재설계는 이미 허용됨 — 기능 정의 Q7=B.)*

- **A) 옛 상태 목록 유지 + 억지 대응** — 루프 활동을 옛 이름에 끼워 맞춤. FE 무변경 / 이름과 실제가 어긋나고(예: "아이디어 형성 중"인데 실제론 여백 검증 검색 중) 새 기능 단계 표현 불가.
- **B) 새 진행 계약: 거시 상태 소수 + 활동 피드** — 상태는 직관적인 몇 개만(접수 → 조사 중 → 보고 작성 중 → 완료/부분 완료/실패), 상세는 **결정 트레이스에서 파생한 활동 피드**("'sparse retrieval' 계열 검색 중 → 논문 4편 깊이 읽는 중")로 표시. 트레이스를 어차피 저장하므로 추가 비용이 작고, deep research류 제품의 표준 표현과 동형. (권장)
- **X) 기타**

[Answer]: B — 새 진행 계약: 거시 상태 소수(접수→조사 중→보고 작성 중→완료/부분 완료/실패) + 결정 트레이스 파생 활동 피드.

#### Q3 — v1에서 에이전트 손에 쥐여줄 도구 목록
루프가 자율 호출할 수 있는 도구를 처음에 무엇으로 제한할까. 도구가 많을수록 능력이 늘지만 통제·비용·검증 부담도 는다. 쟁점은 **우리 코퍼스 밖 arXiv 검색을 처음부터 줄 것인가**.

- **A) 보수적 코어** — 코퍼스 검색(U2) · 근거 형성(문헌탐색 엔진 호출) · GitHub/데이터셋 검색(기존 어댑터) · figure 조회(Q7) · 산출물 저장. **외부 arXiv 검색은 ⑤ 2단계(MCP 연동)에서 추가**하고, **Notion은 루프 밖**(승인 후 별도 실행 — 에이전트가 자율 export 불가). (권장)
- **B) A + 외부 arXiv 검색을 처음부터** — 최신 논문 커버리지↑ / 외부 논문은 DocModel이 없어 본문 수준 근거 검증이 불가 → "근거 등급 낮음" 표시 체계가 추가로 필요해짐.
- **C) A + Notion도 루프 도구로** — 승인 없는 export 금지 규칙(BR-NV17)과 충돌 → 기각 후보.
- **X) 기타**

[Answer]: A — 보수적 코어. 외부 arXiv 검색은 ⑤ 2단계(MCP 연동)에서 추가, Notion은 루프 밖(승인 후 별도 실행).

#### Q4 — 산출물 계약 (잡의 "완성" 정의)
기능 정의(Q3=X)로 산출물이 재편됐다 — **기본 = 유사 연구 표 + 여백 분석 / 온디맨드 = 방향 제안·실험 계획 / export 상태 유지 / 위험 신호 폐기**. 그럼 잡이 "정상 완료"이려면 무엇이 차 있어야 하나.

- **A) 기본 세트 필수 + 온디맨드는 요청 시 생성** — 유사 연구 표·여백 분석(+근거 스냅샷)을 채워야 정상 종료. 방향 제안·실험 계획은 후속 대화 요청이 있을 때만 생성하되 같은 검증 게이트(Q8)를 통과해야 저장. (권장)
- **B) 필수 없음** — 산출물 구성을 에이전트 재량에. *유연 / 결과 예측 불가, 자동 테스트(QT-10) 걸 대상이 약해짐.*
- **X) 기타**

[Answer]: A — 기본 세트(유사 연구 표·여백 분석·근거 스냅샷) 필수, 온디맨드 산출물은 요청 시 생성하되 같은 검증 게이트(Q8) 통과 필수.

### B. 로드맵 ⑤ 단계 수용

#### Q5 — MCP를 코드 어디에 꽂을까
⑤ 2단계에서 외부 서비스(arXiv/GitHub/Notion)를 MCP로 연결한다. **어떤 MCP 서버·제품을 쓸지는 이 설계 사이클의 NFR Requirements 단계(`tech-stack-decisions.md`)에서 결정**하고, 여기서는 아키텍처 위치만 정한다: 루프가 MCP를 직접 아는가, 모르는가.

- **A) 포트 뒤 어댑터** — 루프는 "외부 검색"이라는 포트(인터페이스)만 알고, 그 구현이 MCP인지 일반 API인지 모른다. 기존 헥사고날 원칙(어댑터만 추가, 도메인 불변) 그대로라 테스트 대역·프라이버시 필터(Q11)를 어댑터에 걸기 쉽다. (권장)
- **B) 루프 코어에 MCP 클라이언트 직결** — MCP 서버가 제공하는 도구 목록을 동적으로 그대로 노출. 확장 쉬움 / 도구 통제·프라이버시 경계·테스트가 어려워짐.
- **X) 기타**

[Answer]: A — 포트 뒤 어댑터. MCP 서버·제품 선정은 NFR Requirements 단계(`tech-stack-decisions.md`)에서.

#### Q6 — 세션 메모리의 범위 (⑤ 3단계)
"대화로 조정"이 기능 정의에 들어왔으니(Q4=B), 에이전트가 **무엇을 기억**해야 하는지 정의한다. "이번 잡에 대한 대화"(추가 지시·온디맨드 요청)와 "잡 사이의 기억"(지난 조사 결과·선호 참조)은 다른 것이다.

- **A) 잡 내 대화만** — 이번 조사에 대한 지시·후속 요청만 기억. 잡 간 기억은 범위 밖.
- **B) 잡 간 기억만** — 새 잡이 이전 잡 결과를 참조. 잡 내 대화는 없음. *기능 정의 Q4=B(잡 내 스티어링)와 모순 → 사실상 기각 후보.*
- **C) 둘 다 목표 아키텍처에 정의하고, 잡 내 대화부터 도입** — 기능 정의의 "온디맨드 후속 턴"이 곧 잡 내 대화이므로 이것이 1순위, 잡 간 기억은 그 뒤. 기존 `NoveltyChatMessage` 모델을 잡 내 대화의 저장 모델로 승계. (권장)
- **X) 기타**

[Answer]: C — 둘 다 목표 아키텍처에 정의, 잡 내 대화(온디맨드 후속 턴 포함)부터 도입. `NoveltyChatMessage` 저장 모델 승계.

#### Q7 — 논문 그림·표를 에이전트 눈에 넣는 방식 (⑤ 4단계)
u1 인제스트가 논문의 그림·표·수식을 이미 이미지(WebP)로 잘라 S3에 저장해뒀고, DocModel에 그 목록·캡션이 있다. 조사 중 만난 논문의 figure를 에이전트가 실제로 "보게"(멀티모달 입력) 하는 방식을 정한다. 이 도구는 특정 에이전트 소유가 아니라 **DocModel/S3 자산을 읽는 공용 부품**이다 — 여기서는 novelty 루프가 어떻게 쓸지만 정하고, ⑥ 문헌탐색 에이전트화 때 그쪽 루프에도 노출할지는 ⑥ 질문 게이트에서 별도로 정한다. *주의: 근거 검색·인용 대상을 문장에서 **DocModel 전 객체(표·그림·수식 포함)**로 넓히는 것은 이 질문이 아니라 요구사항 델타 ⑥(Q12)으로 등재된 별도 결정이다 — 본 질문은 그중 "이미지를 LLM 눈에 실제로 넣는 방식"만 다룬다.*

- **A) 온디맨드 도구(`view_figure`)** — 에이전트가 DocModel의 figure 목록·캡션을 보고 "이 그림은 봐야겠다"고 판단한 것만 조회. 이미지는 토큰이 비싸므로 필요한 것만 보는 게 비용·잡음 통제에 유리. (권장)
- **B) 자동 첨부** — 상위 근거 논문의 주요 figure를 일괄로 컨텍스트에 넣음. 발견 가능성↑ / 토큰 비용·잡음↑.
- **X) 기타**

[Answer]: A — 온디맨드 도구(`view_figure`). 캡션 보고 필요 판단한 figure만 조회. (근거 대상 확장은 요구사항 델타 ⑥·로드맵 ⑥ 게이트 몫.)

### C. 안전·비용 (C-2 날조 금지 유지)

#### Q8 — 날조 검사 검문소의 위치
자율 루프에서 "근거 없는 내용 금지"를 코드로 강제하는 검사를 어디에 두나. 검사 자체는 결정론(LLM이 아닌 코드가 판정)이라는 원칙은 불변.

- **A) 저장 시점마다 검사** — 에이전트가 산출물 저장 도구를 부를 때마다 근거 링크 실재성·필수 필드·범위 규칙을 코드로 검사하고, 위반이면 **저장 거부 + 이유 반환**(에이전트가 고쳐서 재시도). 문제를 즉시 잡아 예산 낭비가 없고, U7 요약의 결정론 게이트와 같은 원리. (권장)
- **B) 끝날 때 일괄 검사** — 구현 단순 / 위반을 늦게 발견해 그때까지의 루프 비용이 낭비되고, 부분 실패 처리 복잡.
- **C) LLM에게 검사시킴** — 결정론 원칙과 상충 → 기각 후보.
- **X) 기타**

[Answer]: A — 산출물 저장 시점마다 결정론 검사, 위반 시 저장 거부 + 이유 반환(재시도 기회).

#### Q9 — 루프 폭주 방지 (예산)
자율 루프는 방치하면 같은 검색을 무한 반복할 수도 있다. 무엇으로 막나. (구체 수치는 NFR 단계로 — 여기선 정책만.)

- **A) 3중 한도** — ① 최대 반복 수 ② 도구 호출 수(도구별 상한 포함) ③ 토큰/비용 한도(비용 판단은 U6 단일 권위 유지). 소진 시 그때까지 **검증된** 산출물만으로 "부분 완료(degraded)" 종료. (권장)
- **B) 비용 한도만** — 단순 / 저비용 무한 반복(같은 검색 반복)을 못 막음.
- **C) 무제한** — 기각 후보.
- **X) 기타**

[Answer]: A — 3중 한도(최대 반복 수 + 도구 호출 수 + 토큰/비용, U6 단일 권위). 소진 시 검증된 산출물로 부분 완료 종료. 수치는 NFR로.

#### Q10 — 취소와 재개
사용자가 실행 중 "그만"을 눌렀을 때, 그리고 중단된 조사를 이어가고 싶을 때의 동작.

- **A) 협조적 취소 + v1은 재개 없음** — 취소 신호가 오면 지금 도는 도구 호출만 마치고 루프 탈출, 이미 저장·검증된 산출물은 유지(취소됨 상태). 이어가기는 새 잡으로 하되 세션 메모리(Q6)가 이전 결과를 참조. (권장)
- **B) 체크포인트 재개** — 루프 상태(대화 이력·도구 결과)를 저장해뒀다가 그 지점부터 재개. 가치 있음 / 상태 저장·버전 관리 복잡도가 큼.
- **C) 즉시 강제 종료** — 진행 중이던 호출 결과 유실·데이터 정합성 위험.
- **X) 기타**

[Answer]: A — 협조적 취소, v1 재개 미지원(이어가기는 세션 메모리를 참조하는 새 잡으로). 체크포인트 재개는 필요 확인 시 재론.

#### Q11 — 밖으로 나가는 데이터의 경계 (프라이버시)
외부로 나가는 도구(GitHub·데이터셋·향후 arXiv MCP)에 사용자 원고 원문·근거 전문이 흘러나가면 안 된다(BR-NV6 승계). 에이전트가 도구 인자를 자유롭게 지어내므로, 막는 장치는 기계식이어야 한다.

- **A) 도구별 허용 목록 + 어댑터 차단** — 외부로 나갈 수 있는 것(주제·키워드·논문 제목·기술명·익명화 요약)을 도구마다 규칙으로 명시하고, 에이전트가 뭘 넣든 **어댑터가 기계적으로 걸러서** 위반 payload는 차단. (권장)
- **B) 제한 없음(외부 서버를 신뢰 경계 안으로)** — 프롬프트 인젝션 경유 유출 경로가 열림 → 기각 후보.
- **X) 기타**

[Answer]: A — 도구별 허용 payload 목록 + 어댑터의 기계식 차단(BR-NV6 승계·확장).

#### Q13 — 규칙 문서(business-rules.md)의 서술 방식
기존 19개 규칙(BR-NV1~19)이 있는 상태에서 v2 규칙 문서를 어떻게 쓰나.

- **A) 승계 표 + 델타 중심** — 기존 규칙 각각에 유지/개정/폐기 판정 표를 두고(예: 위험 신호 규칙 → 폐기, 근거 링크 규칙 → 유지), 루프에서 새로 생긴 규칙만 상세히 쓴다. 무엇이 왜 바뀌었는지 추적이 쉽고, ⑤ 구현 때 대조하기 좋다. (권장)
- **B) 전면 재작성** — 새 체계로 처음부터. 일관성 / 현행 대비 변경점 추적이 어려움.
- **X) 기타**

[Answer]: A — BR-NV1~19 승계/개정/폐기 판정 표 + 루프 신설 규칙 상세.

#### Q14 — "근거 먼저" 규칙의 강제 방식
현행 규칙 BR-NV2 = 자연어 잡은 **근거 형성(문헌탐색 엔진 호출)부터** 하고 시작한다(근거 없이 떠도는 조사 방지). 자율 루프에서 이걸 어떻게 유지하나.

- **A) 선행 강제 유지** — 자연어 잡은 루프 시작 전(또는 강제된 첫 도구로) 근거 형성을 실행. 근거 위에서만 조사가 출발. (권장)
- **B) 순서는 자율, 결과물로만 강제** — 호출 시점은 에이전트 재량이되, 근거 스냅샷 없이는 여백 분석 저장이 거부됨(Q8 게이트). 자율성↑ / 근거 없이 외부 검색부터 도는 경로가 열림.
- **X) 기타**

[Answer]: A — 선행 강제 유지(자연어 잡은 근거 형성부터). 근거 위에서만 조사가 출발.
