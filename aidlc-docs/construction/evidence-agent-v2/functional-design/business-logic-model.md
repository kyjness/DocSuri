# Evidence Agent v2 (U11) — 비즈니스 로직 모델 (Business Logic Model)

**단계**: CONSTRUCTION → Functional Design (재설계 라운드) · **유닛**: U11 문헌탐색·근거형성 · **일자**: 2026-07-28
**원칙**: 기술 무관 — 알고리즘·흐름·정책의 **형태**만. 수치(상한·타임아웃·임계)와 구체 기술은 NFR/Infra.
**근거**: 요구사항 게이트 Q1~Q15 · FD 게이트 Q1~Q12 · `domain-entities.md` · `business-rules.md` · `requirements.md` FR-36~38·FR-45~47 · D5 계약.

## 0. 개관 — 턴 수명주기

```
[U6 GATEWAY] authn · authz(SEC-8) · rate-limit(SEC-11) · cost-state(NFR-C1)
      ▼
0. loadOrCreateSession
      ▼
1. costGate          U6 get_budget_state() 단일 권위 → 저하면 abstain(cost_degraded)
      ▼
2. validateAttachments  형식·크기 검증(BR-EV-4) — 실패 시 루프 시작 전 반환
      ▼
3. routeLength       단순 → 동기 SSE / 복잡(승격 다수·첨부) → 비동기 잡
      ▼
4. LOOP  ┌────────────────────────────────────────────────┐
         │ observe : 확보 논문 · 누적 근거 · 최근 도구 결과   │
         │           (+ 호출 인자, + 1회성 이미지 첨부)      │
         │ decide  : 다음 도구·인자 선택 or 종료 판단         │
         │ act     : 예산 검사 → 도구 실행 → ToolCallRecord  │
         └────────────────────────────────────────────────┘
      ▼ 종료
5. assemble          누적 근거 → 비교표·쟁점 오버레이 (결정론, LLM 없음)
      ▼
6. abstainCheck      누적 근거 0건 → EvidenceAbstainResult (INV-EV-2)
      ▼
7. persist           턴 결과 + 트레이스 저장
      ▼ SSE / 폴링
[ 클라이언트(U5): 활동 피드 · 비교표 · 근거 칩 렌더 ]
```

**v1과의 차이**: 2~5단계가 고정 순서(검색 1회 → DocModel 로드 → 추출 1회 → 조립)였다. v2는 4단계가 루프이고, 조립만 결정론으로 남는다.

## 1. 루프 코어

### 1.1 observe
관찰에 싣는 것: 확보한 `PaperHandle` 목록(출처·범위 포함), 누적 근거 현황(건수·인용 논문 수·상충 유무), 최근 도구 결과 요약, 남은 예산 요약.

- **결과 줄에는 호출 인자를 함께 싣는다** — `[seq] 도구명(인자) (상태)`. 결과만 보이면 모델은 그것이 어떤 호출에서 나왔는지 몰라 같은 질의를 반복하고, 그 반복이 캡을 태워 근거를 못 채운 채 종료한다(novelty 실측).
- **이미지 첨부는 `decide` 직후 소비하고 폐기한다** — 도구 실행 뒤에 두면 종료 제안이 거부돼 도구 없이 되도는 경로에서 재전송이 남는다.
- **도구 결과는 신뢰 경계 밖 데이터**다. 시스템 지시 구획과 분리하고, 그림 안의 문구는 지시가 아님을 프롬프트가 명시한다(prompt injection 방어).

### 1.2 decide
LLM이 다음 행동(도구 + 인자) 또는 종료를 고른다. 고정 단계 순서는 없다. **질의 설계·깊이 판단·종료 판단이 자율의 전부**이며, 추출·검증·조립은 결코 LLM 재량이 아니다(상속 arch Q2=A).

### 1.3 act
예산 검사 → 도구 실행 → `ToolCallRecord` 기록.

- 상한 초과 시 도구를 실행하지 않고 `budget_denied`를 기록한 뒤 종료 경로로 간다.
- 도구 실패는 턴을 깨지 않는다 — 오류를 관찰에 실어 다음 `decide`가 다른 행동을 고르게 한다. **거부 사유는 판정이자 수리 지시**여야 한다("무엇이 틀렸는지 + 다음에 무엇을 하면 되는지"). 그렇지 않으면 루프가 같은 실수를 반복한다(⑤2 교훈).

### 1.4 종료 판단
| 사유 | 조건 |
|---|---|
| `sufficient` | 에이전트가 충분하다고 판단 — 단, 누적 근거가 0건이면 정상 종료로 인정하지 않는다 |
| `budget_exhausted` | 반복·도구 캡·토큰 한도 소진 |
| `no_evidence` | 탐색을 마쳤으나 게이트 통과 근거 0건 → 기권 |
| `fatal_error` | 복구 불가(권한·필수 입력 결손) |

## 2. 도구 계약 (FD 게이트 Q1=A)

| 도구 | 하는 일 | 경계 |
|---|---|---|
| `corpus_search(query, mode?)` | 내부 코퍼스 하이브리드 검색(U2 재사용). `mode="phrase"`면 정확 문구 검색 | 전용 인덱스·랭킹 금지. 점수 미노출(INV-EV-5) |
| `external_search(query)` | 코퍼스 밖 논문 검색 — **제목·초록만** 확보 | payload allowlist(질의·키워드만). 결과는 아직 근거가 아니다 |
| `fetch_paper(paperRef)` | **온디맨드 승격** — 본문 취득 + DocModel 생성 요청 | DocModel writer는 U1 — U11은 요청만 한다. 실패는 `abstract` 범위 유지 |
| `read_paper(paperRef, section?)` | 확보 논문의 DocModel 블록 읽기 | 읽기 전용 |
| `view_figure(paperRef, assetId?)` | 그림·수식 조회 — 2모드(목록 / 이미지) | 매니페스트에 실재하는 자산만. 목록 조회도 캡 1회 소비 |
| `extract_evidence(paperRefs, focus)` | 근거 추출 + **게이트 통과분만 누적** | 근거가 쌓이는 유일한 경로 |

**루프 밖**: 세션 삭제·초기화, 예산 재배분. 레지스트리는 allowlist deny-by-default — 어휘 밖 도구는 구조적으로 등록 불가.

### 2.1 `extract_evidence`와 게이트의 접점
호출마다 §3의 게이트를 돌리고 **통과분만** `EvidenceAccumulator`에 넣는다. 반환 요약에는 통과/탈락 건수와 탈락 사유 분포가 실려, 다음 `decide`가 "더 읽을지 / 다른 논문으로 갈지"를 판단할 수 있다. 탈락 상세(어떤 quote가 왜)는 사용자에게 노출하지 않는다(INV-EV-5).

## 3. 날조 검사 게이트 (C-2 — 기계식, LLM-judge 없음)

`extract_evidence`가 만든 각 `SourceRef`에 대해 순서대로 검사한다. 하나라도 실패하면 그 출처를 버리고, 지지 출처가 0이면 그 근거 줄을 버린다.

| # | 검사 | 대상 |
|---|---|---|
| 1 | `quote`가 존재하고 최소 길이 이상인가 | 전 범위 |
| 2 | `quote`가 출처 텍스트에 **글자 그대로** 있는가 | `fulltext`=DocModel 투영 / `abstract`=취득한 초록 |
| 3 | **`quote`가 `anchor`가 가리키는 그 블록의 투영 안에 있는가** | `fulltext` — **v2 신설**(v1은 문서 어디든 있으면 통과했다) |
| 4 | `anchor`가 그 논문에 실재하는 블록 id인가 | `fulltext` |
| 5 | `statement`의 숫자 ⊆ 검증된 quote들의 숫자 | 전 범위 |
| 6 | 그림 유래 주장의 숫자가 **그 논문 텍스트(캡션·본문·표)에 실재**하는가 | `figure` — **v2 신설** |

**블록별 대조 대상**: `paragraph`·`code`=본문 텍스트 / `list`=항목 텍스트 / `table`=캡션 + 행 직렬화 / `formula`=LaTeX / `figure`=캡션.

> **표기 정합**: 프롬프트에 싣는 블록 표현과 대조에 쓰는 투영은 **같은 문자열 규칙**을 써야 한다. v1은 캡션을 프롬프트에서 `"Figure 2: ..."`, 투영에서 `"Figure 2 ..."`로 만들어 캡션 인용이 구조적으로 탈락했다 — 단일 함수로 통일한다.

**그림 근거(`sourceScope=figure`)의 취급**: 검사 6을 통과한 정성 서술(추세·구조)은 기계 검증이 불가능하므로 **차단하지 않고 범위를 표시**한다. 검증 강도 차이를 감추지 않는 것이 이 등급의 목적이다.

## 4. 온디맨드 승격 경로 (FR-31 등급 체계)

```
external_search → 제목·초록 (빠름)
      ▼ 에이전트가 선별
fetch_paper
   ├─ 1. 본문 취득 (arXiv: ar5iv HTML 우선 · PDF+GROBID 폴백)  ┐ 동기
   ├─ 2. DocModel 구성 (섹션·표·수식·앵커)                      ┘ — 이번 턴 인용에 필요
   └─ 3. 청킹·임베딩·색인                                        ← 백그라운드(비차단)
      ▼
   promoted → PaperHandle.scope = fulltext
   license_blocked / parse_failed → scope = abstract 유지 (배제하지 않는다)
```

- **1·2는 동기, 3은 백그라운드**다. 3은 "그 논문이 앞으로 **검색에** 걸리게" 하는 작업이라 이번 답변의 인용에는 필요 없다. 3의 실패는 답변에 영향을 주지 않는다(부수 경로 비차단 원칙).
- **DocModel 단일 writer는 U1**이다. U11은 U1의 빌드 경로를 호출해 요청할 뿐 직접 쓰지 않는다.
- 승격 비용(취득·파싱·임베딩)은 `LoopBudget`에 계상한다(FR-45).

## 5. 조립과 확인 범위

### 5.1 조립 (결정론)
누적 근거를 **논문 간 비교형**으로 재편하고(BR-EV-5 승계), 상충 출처가 있는 명제를 쟁점으로 강조한다. LLM 호출 없음 — 입력이 같으면 출력이 같다.

### 5.2 확인 범위 (v2 신설)
탐색이 완결되지 않았어도 검증된 근거가 1건 이상이면 **성공으로 반환**하고, `EvidenceCoverage`에 `examined`/`candidates`/`stoppedReason`을 싣는다. 터미널 상태는 `ok|abstain` 2종을 유지한다(D5 union 불변 → U12·FE 분기 무영향).

화면 문구는 수치로 쓴다: *"관련 논문 12편 중 5편까지 확인했습니다. 이어서 확인할까요?"* — 내부 용어(`degraded`)는 노출하지 않는다.

## 6. 진행 표시 (FR-36 v2, FR-46)

- **거시 상태**: 접수 → 조사 중 → 정리 중 → 완료 / 부분 / 기권.
- **활동 피드**: `ToolCallRecord`에서 파생한다 — 도구명, 질의 요약, 확인 건수, 승격 상태, 저하 사유. **별도 이벤트 스트림을 두지 않는다**(두 벌이면 화면 기록과 감사 기록이 어긋나고 재접속 복원이 불가능하다).
- SSE는 트레이스 append를 흘리고, 비동기 잡·재접속은 저장된 트레이스를 읽는다.
- 노출 경계: 내부 payload·자격증명·게이트 탈락 상세·벡터 점수는 제외(SEC-9, INV-EV-5).

## 7. 멀티턴 (FR-36)

이전 턴의 인용 논문·근거·질의가 `AgentRunContext.session`으로 들어가고, **후속 질문의 해석은 루프의 판단**이다. v1의 정규식 분류기(정확 문구·꼬리질문 패턴)와 topic 이어붙이기는 폐기한다 — "그중에서 데이터가 적을 때는?" 같은 질문에서 무엇을 좁힐지는 이전 턴 맥락을 읽은 `decide`가 정한다.

---

## 8. D5 포트 소비 (U12)

`EvidenceFormationPort.form_evidence(request, ctx)` 시그니처와 **동기 완료 보장을 유지**한다. 내부만 루프로 교체하고, 호출자 예산에 맞춰 `LoopBudget`을 축소 배분한다. U12는 `SourceRef`의 추가 필드를 무시해도 안전하다.
