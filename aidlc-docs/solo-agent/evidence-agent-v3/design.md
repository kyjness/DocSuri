**단계**: 로드맵 ⑩-1 (두 에이전트 완성 — evidence)

---

## 1. 목적·범위 (확정)

> **evidence는 문헌에 근거해 답하는 챗봇이다.**
> 사용자가 던진 주장이나 질문에 대해, 논문을 찾아 읽고, 인용을 달아, **판단까지 포함한 답변**을 한다.
> 근거를 못 찾으면 답을 지어내지 않고 못 찾았다고 말한다.

- 판단은 **조건부**로 한다 — 문헌이 갈리면 갈린 채로 보여주되 무엇이 가르는지를 밝힌다. 종합해 한쪽으로 단정하지 않는다.
- 못 찾으면 **부분 답 + 다음 행동**을 준다.
- 대화 안에서 끝난다 — 침묵 금지 · 언제든 취소 · 취소해도 부분 결과.

**범위 밖**: 논문 추천·요약 자체(U7), 새 연구 방향 제안(novelty), 논문 외 출처(웹·뉴스). 이런 요청은 §2.4의 방식으로 안내한다.

**불변 제약** (v2에서 승계): C-2 날조 금지 — 인용·수치는 기계식으로 검증되고 LLM-judge를 쓰지 않는다. 비용 판단은 U6 `get_budget_state()`만 한다.

## 2. 대화 동작 — 사용자가 보는 것 (2026-08-21 확정)

### 2.1 답변 모양 — 산문 판단 + 근거표

채팅에 **대화하듯 산문으로 판단**이 먼저 오고, 그 아래 **근거표**(논문 대조표, BR-EV-5 승계)가 붙는다. 구획 라벨·카드는 쓰지 않는다.

```
데이터가 적고 도메인이 사전학습과 가까울 때는 LoRA가 비슷하거나 더 나은
성능을 내요[1][2]. 반면 도메인이 크게 다르거나 학습량이 클 때는 전체
파인튜닝이 앞서요[3]. 갈리는 지점은 '적응 과제가 사전학습 분포 안에
있느냐'예요.

┌────────────────────────┬────────────────┬────────────┐
│ 명제                   │ 지지           │ 상충       │
├────────────────────────┼────────────────┼────────────┤
│ 저데이터·근접 도메인   │ [1] Hu 2021    │            │
│ → LoRA 동등 이상       │ [2] Dettmers 23│            │
│ 도메인 차이 큼         │ [3] Biderman 24│ [1] Hu 2021│
│ → 전체 파인튜닝 우세   │                │            │
└────────────────────────┴────────────────┴────────────┘
  [n] 을 누르면 원문 인용(절·표·그림 위치)으로 이동
```

**판단 문장의 두 종류.** `[n]`이 붙은 문장은 그 근거가 실제로 그 논문에 있음을 기계가 확인한 문장이다. 번호 없는 문장(위의 "갈리는 지점은 …")은 **모델이 근거들을 종합해 쓴 문장**이라 기계가 확인할 수 없다. 화면에서 구분한다 — 숨기지도, 같은 급으로 보이게 하지도 않는다. 구분 방식(배지·색)은 §8.

### 2.2 문헌이 갈릴 때

한쪽으로 단정하지 않는다. **어떤 조건에서 어느 쪽인지**를 말하고, 갈림 지점을 한 문장으로 밝힌다.

```
○  "데이터가 적을 때는 LoRA[1][2], 도메인이 다를 때는 전체 파인튜닝[3]. 갈리는 지점은 ~."
✗  "대체로 LoRA가 유리합니다."      ← 근거로 확인할 수 없는 단정
✗  "논문마다 다릅니다."             ← 판단을 안 한 것
```

근거표에서 상충은 같은 행의 `상충` 열에 놓이고, 상충 있는 명제를 표 위쪽에 둔다(BR-EV-5).

### 2.3 근거가 부족하거나 없을 때

**대화가 끊기지 않는다.** 찾은 만큼 답하고, **탐색이 잘렸을 때만** 어디까지 봤는지 한 줄 붙이고, 다음 수는 산문으로 제안한다. 버튼은 없다 — 사용자가 타이핑으로 이어간다.

```
[부분 — 근거는 있으나 한쪽만]
  데이터가 적을 때 LoRA가 유리하다는 근거는 있어요[1]. 반대 조건(도메인이 크게
  다를 때)을 다룬 논문은 확인한 범위에서 찾지 못했어요.
  후보 24편 중 8편까지 보고 멈췄어요 — 이어서 더 찾아볼까요?
  (근거표 1행)

[없음 — 후보는 있었음]
  이 질문에 대한 근거를 확인한 논문에서 찾지 못했어요. 후보 12편을 모두 봤어요.
  질문을 다른 표현으로 바꾸거나, 범위를 넓혀 다시 물어봐 주세요.

[없음 — 후보조차 없음]
  이 주제를 다룬 논문을 찾지 못했어요. 주제를 넓히거나 다른 용어로 물어봐 주세요.
```

"확인 범위" 한 줄은 **예산·취소·실패로 잘렸을 때만** 나온다(v2 Q10 승계). 충분해서 멈춘 정상 답변에는 안 나온다. 무엇을 제안할지는 멈춘 이유에 따른다 — 예산이면 "이어서", 후보가 없으면 "넓히기", 후보는 있는데 근거가 없으면 "다른 표현".

### 2.4 문헌으로 답할 수 없는 질문

잡담·코드 작성·개인 의견·논문 외 출처 — 검색을 시작하지 않고 바로 답한다.

```
Q. 오늘 뭐 먹을까?
   저는 논문에서 근거를 찾아 답하는 도우미예요. 이런 질문을 해보세요 —
   "LoRA가 전체 파인튜닝보다 좋아?" / "RAG가 긴 문맥 모델보다 정확해?"
```

판정은 루프 안의 모델이 한다(별도 분류기 없음 — novelty 세션 메모리 때와 같은 원칙). 단 **검색을 한 번도 안 했을 때만** 허용된다 — 검색 뒤의 "범위 밖"은 §2.3의 "없음"으로 처리한다.

### 2.5 후속 질문

같은 세션의 이전 대화를 기억한다. **턴 수가 아니라 토큰 예산으로** 자른다 — 최근 턴은 약 8천 토큰까지 그대로(질문·답변 요약·인용 논문, 턴당 약 400토큰이라 약 20턴), 넘치면 오래된 것부터 한 단락 요약으로 접는다. **인용한 논문 id는 세션 전체를 유지**한다(짧아서 부담이 없고, 후속 질문이 그 목록 위에서 돈다). 8천은 시작값이며 실측 후 조정한다.

후속 질문은 그 위에서 좁히거나 넓힌다.

```
턴 1  "LoRA가 전체 파인튜닝보다 좋아?"   → 논문 A B C 인용
턴 2  "그중에서 2023년 이후만"           → A B C 중 2023+ 만 다시 봄, 새 검색 없음
턴 3  "이어서 더 찾아줘"                 → 같은 질문, 아직 안 본 후보부터
턴 4  "QLoRA는?"                        → 새 주제. 새로 탐색하되 A B C는 후보에 남김
```

### 2.6 논문을 찾는 곳 — 코퍼스 먼저, 없으면 같은 원천에서 실시간 조회

코퍼스는 ingestion이 **arXiv·S2·OpenAlex**에서 수집해 둔 논문이다. 원래 목표(세 원천 약 10년치)대로 수집됐으면 코퍼스만으로 충분하지만, 지금은 기반 논문 약 4,000편이라 **코퍼스에 없는 논문을 같은 세 원천에서 질문 시점에 가져온다.** 이것은 "외부 검색"이 아니라 **실시간 조회**다 — 원천이 같다.

```
1. 코퍼스 검색 (하이브리드, U2 재사용)
2. 부족하면 → arXiv · S2 · OpenAlex 실시간 조회 (초록만 옴)
3. 본문이 필요하면 → 그 자리에서 가져와 파싱(온디맨드 승격, v2 Q5=B)
4. 실시간으로 찾은 논문은 백그라운드로 색인 → 쓸수록 코퍼스가 그쪽으로 자란다
```

- 실시간 조회는 지금 arXiv API 하나인데 **세 원천으로 맞춘다.** 수집하는 곳과 찾는 곳이 같아야 "시스템이 알 수 있는 것 = 찾을 수 있는 것"이 된다. 클라이언트·ID 정규화·중복 제거는 ingestion 것을 재사용한다.
- 코퍼스가 목표치에 가까워져도 설계는 바뀌지 않는다 — 실시간 조회를 부르는 횟수만 줄어든다.
- **논문 밖 출처(GitHub·데이터셋)는 찾지 않는다.** 검증이 안 돼서가 아니라, 그 출처가 이 에이전트의 질문("문헌상 이 주장이 맞나")에 답하지 않기 때문이다. "구현체가 있나"는 novelty의 질문이다.

### 2.7 진행 중

누르자마자 **수락** 신호가 오고, 그 뒤 도구를 부를 때마다 한 줄씩 쌓인다. 취소는 처음부터 끝까지 가능하다.

```
● 코퍼스 검색 "LoRA full fine-tuning comparison" → 24편 (제목·초록)
● 본문 확보 — Hu 2021, Dettmers 2023
● 본문 읽는 중 — Hu 2021 (문단·표·수식 87블록)
● 그림 보는 중 — Hu 2021 Figure 2
● 근거 추출 — 3건 확보 (2건 탈락)
● 실시간 조회 (S2) → 6편
● 본문 확보 — Biderman 2024
                                              [취소]
```

검색 결과에 제목·초록이 같이 오므로 "초록 확인"은 별도 단계가 아니다. 모델이 읽을 논문을 고르면 **DocModel 전 블록**(문단·리스트·표·그림 캡션·수식·알고리즘, Q1=A)을 읽고, 그림·수식 자체가 필요하면 비전으로 본다(`view_figure`).

활동 줄에는 **논문 제목·건수·단계**만 싣고 인용문은 싣지 않는다 — 검증 전 문장이 화면에 나오면 안 된다(C-2).

### 2.8 취소

취소하면 **지금 하던 한 단계가 끝나는 대로** 멈춘다(보통 수 초). 그 시점까지 검증된 근거로 §2.3의 부분 답을 만든다 — "취소됨 · 후보 24편 중 5편 확인"이 확인 범위 한 줄로 붙는다. 멈추는 사이 실행된 도구의 결과도 부분 답에 들어간다.

### 2.9 비용 한도

- **시작 전**에 한도면: "오늘 이용량에 도달했어요. 내일 00:00에 다시 열려요." 이전 답 다시 보기는 된다.
- **도중**에 한도면: 취소와 같은 경로 — 부분 답 + "내일 이어서 찾을 수 있어요".

"제한" "degraded" 같은 내부 용어는 쓰지 않는다(v2 Q10 승계).

## 3. 루프·도구

### 3.1 그래프 (LangGraph, Q5=B)

한 턴은 LangGraph `StateGraph` 하나다. 상태는 현행 `LoopState`(확보 논문·후보·누적 근거·트레이스·노트)에 §3.3의 필드를 더한 것이고, 체크포인트는 **Postgres saver**(이미 있는 DB)에 super-step마다 남는다. `thread_id = turn_id`.

```
          ┌─────────────────────────────────────────────┐
          ▼                                             │
 [decide] ── 도구 호출 ──▶ [act] ── 결과를 관찰에 ───────┘
    │
    ├─ 종료 제안 ──▶ [check_floor]  바닥 미달이면 사유를 노트에 싣고 decide로
    │                    │ 통과
    │                    ▼
    │                [answer]  검증된 근거만 보고 산문 판단을 쓴다 (§4)
    │                    ▼
    │               [assemble]  근거표·확인 범위·답변 검사 → 결과
    │
    └─ 범위 밖 제안 ──▶ [check_scope]  검색 0회일 때만 통과 → 안내문으로 종료 (§2.4)

 예산 소진 / 취소 / 치명 오류 ──▶ [answer](근거 있으면) ──▶ [assemble]
```

- **노드는 평범한 파이썬 함수**다. `decide`는 현행 Bedrock 어댑터를 그대로 부르고, `act`는 현행 `ToolRegistry`를 그대로 쓴다 — 이 이전에서 LLM 연결은 손대지 않는다. (LangChain 도입 여부는 이 문서가 정하는 것이 아니라 미결이다 — 질문지 Q5 정정 블록 참조.)
- 현행 `run_loop()`의 불변 조건은 그대로 노드에 산다 — 예산 검사는 act 직전 1회, 도구 호출은 `ToolCallRecord` 1:1, 이미지는 decide 직후 소비.
- **PR 1**은 이 그래프로 옮기되 `answer` 노드 없이(현행 `_narrative`), `check_floor`는 현행 규칙(근거 0건 거부)만으로 만든다 — 동작 변화 0을 증명한 뒤 PR 2에서 나머지를 얹는다.
- **PR 1 실행 결과(2026-08-23, `feature/evidence-langgraph-loop`)**: 노드 3개(`decide`/`check_floor`/`act`), `compile()`에 체크포인터 없음 — `LoopState`가 doc_model·이미지를 들고 있어 직렬화가 안 되므로 **Postgres saver·`thread_id=turn_id`는 PR 2**(상태 직렬화와 함께). `finish`/`assemble` 노드도 없다 — runner가 여전히 `assemble()`을 부르고 종료는 `_finish` 4곳이 `outcome`을 채우는 것으로 표현된다; PR 3이 이를 `answer → assemble` 꼬리로 모은다. 스텝 상한은 예산에서 유도: `_STEPS_PER_ITERATION(2)·n + _TAIL_STEPS(1) + 1`(LangGraph 1.2.x는 N스텝에 limit ≥ N+1, 실측). PR 3의 `answer`·`assemble`은 꼬리 스텝이라 `_TAIL_STEPS`를 올린다. 배포는 `langgraph==1.2.11` 정확 고정(상한이 여유 없이 잡혀 있어서). LangSmith 자동 트레이싱은 `tracing_context(enabled=False)`로 차단.
- **PR 2 실행 결과(2026-08-24, `feature/evidence-turn-execution`)**: 그래프 채널은 **순수 JSON**(`snapshot`·`proposal{kind}`·`outcome{reason,detail}`)이고 살아 있는 `LoopState`·deps는 `context_schema=LoopRun`으로 주입된다(체크포인트 밖). Postgres saver가 super-step마다 저장한다(`thread_id=turn_id`, 풀은 autocommit).
  - **스냅샷에는 마감(`assemble`)이 읽는 것만 싣는다.** DocModel·투영 캐시·이미지는 직렬화가 안 되고, 도구 결과 관찰 윈도우·소모 예산·후보 논문의 초록 본문은 되읽는 소비자가 없다. 상태를 **바꾼 노드만** 돌려준다(`act`와 종료 지점) — `decide`·`check_floor`가 만지는 것은 예산·이미지·노트뿐이고, 매 노드가 전체 투영을 다시 쓰면 같은 바이트가 blob과 writes에 두 번씩 쌓인다. 실측: 7도구 턴 체크포인트 16건·**59.7 kB**(초안대로 전부 실었을 때는 9도구 턴에 22건·493 kB였다).
  - **완료된 thread는 다시 invoke해도 아예 돌지 않는다**(입력 쓰기조차 반영되지 않는다 — 1.2.x 실측). 그래서 `run_loop`는 invoke 전에 스레드를 비운다: 재배달된 잡이 "아무 일도 안 하고 성공"으로 끝나는 것을 막는 유일한 방법이다. 재개가 아니라 새 실행이므로 이 줄은 PR 4 이어가기가 먼저 걷어내야 한다.
  - 그래프는 **`TurnCheckpoints`가 소유**하고 프로세스당 한 번 컴파일한다. 러너는 그 그래프를 받아 돌리기만 하고, 스냅샷 조회·삭제는 체크포인트 객체 책임이다 — 러너에 매달았더니 세션 삭제·취소·이벤트·폴링 5개 라우트가 LLM 러너에 묶여, 러너가 구성되지 않는 배포에서 세션 삭제가 500이 됐다.
  - 취소·중단은 `deps.should_stop`이 `decide` 진입(super-step 경계)에서 사유를 돌려주는 것으로 표현한다 — `RunControl.request_drain()`은 예외(`GraphDrained`)로 빠져 꼬리와 한 길이 아니라 쓰지 않았다. `_finish`는 `FATAL_ERROR`·`CANCELLED`·`INTERRUPTED`를 근거 0건이어도 강등하지 않는다.

### 3.2 도구

| 도구 | 현행 대비 | 턴당 상한 |
|---|---|---|
| `corpus_search` | 유지 + **`year_from`·`year_to` 인자 추가** — §2.5의 "2023년 이후만"과 "최근 연구는?"에 답하려면 연도 제약이 프롬프트 당부가 아니라 인자여야 한다 | 5 |
| `live_lookup` | `external_search`의 **이름·범위 변경** — arXiv 하나에서 **arXiv·S2·OpenAlex 셋**으로. 클라이언트·ID 정규화·중복 제거(승자 arXiv > S2 > OA)는 ingestion 것을 포트 뒤에서 재사용. 결과는 초록만. 소스별 서킷 브레이커(novelty `SourceBreaker` 공유) | 3 (세 소스 합산) |
| `fetch_paper` | 유지 — 온디맨드 승격(v2 Q5=B), 파싱은 동기·색인은 백그라운드 | 3 |
| `read_paper` | 유지 | 8 |
| `view_figure` | 유지 | 6 |
| `extract_evidence` | 유지 + **`stance` 인자 추가**(`support \| counter \| neutral`) — §3.3의 바닥 검사 재료. 모델이 "반대 근거를 찾는 중"이라고 **선언**하게 해서 시스템이 셀 수 있게 한다 | 8 |

검색 도구 둘(`corpus_search`·`live_lookup`)에도 같은 `stance` 인자를 둔다. 인자는 트레이스에 남으므로 "반대 측을 찾았는가"가 기계적으로 판정된다. 프롬프트 당부("반대 근거도 찾아라")로 두지 않는 이유는 novelty에서 당부가 지켜지지 않는 것을 실측했기 때문이다(루프 미사용 사례). 모델이 stance를 잘못 붙일 수 있으므로 §6 기계 채점에 "반대 측 탐색 여부"를 둔다.

**explicit scope**(사용자가 논문을 지정)는 현행대로 검색 도구 둘을 **등록하지 않는다** — 프롬프트가 아니라 구조로 막는다(BR-EV-2).

### 3.3 종료 조건 — 바닥과 천장

현행은 "근거 0건이면 거부" 하나다. 바닥을 둘로 올린다(2026-08-21 확정).

**바닥** (이 아래로는 정상 종료 불가):
1. 검증 통과 근거 ≥ 1건 (INV-EV-2 승계)
2. 질문이 **주장·비교형**이면 `stance=counter`로 표시된 검색 또는 추출이 ≥ 1회

**천장**: 예산(반복 12 · 도구 30회 · $0.50, 현행 수치 유지 — `answer` 단계 비용도 이 한도에 계상).

그 사이는 모델이 정한다. 바닥 미달 종료 제안은 거부하고 **미달 사유를 노트에 실어** 다음 decide가 달라지게 한다(현행 `_NO_EVIDENCE_NOTE` 방식).

**질문 유형**은 첫 decide에서 모델이 선언한다 — `question_kind: claim | comparison | fact | out_of_scope`. 상태에 저장되고 트레이스에 남는다. `fact`("X는 몇 년에 나왔어")는 반대 측 조건을 면제한다. 별도 분류기는 두지 않는다.

**범위 밖**(`out_of_scope`)은 검색 0회일 때만 종료로 인정한다. 검색을 한 뒤의 범위 밖 제안은 "후보 없음"(§2.3)으로 처리한다 — 비용을 쓰고 나서 안 하겠다고 하는 길을 막는다.

### 3.4 후속 질문과 이어가기

관찰에 싣는 이전 대화는 §2.5의 규칙을 따른다 — 토큰 예산(8천)까지 최근 턴 그대로, 그 이전은 요약 한 단락, 인용 논문 id는 세션 전체. 현행 `_PRIOR_TURNS = 3`은 근거 없이 옮겨온 수치라 폐기한다. 요약은 예산을 넘기는 턴이 생길 때 한 번 만들어 세션에 저장하고(매 턴 재요약하지 않는다), 이후 턴이 밀려날 때마다 그 요약에 덧붙인다. 여기에 둘을 더한다:

- **이어가기**("이어서 더 찾아줘"): 직전 턴의 체크포인트에서 **후보 목록(발견했으나 안 읽은 논문)과 확인한 논문 집합**을 새 턴의 씨앗으로 옮긴다. 검색부터 다시 하지 않는다. 판정은 모델이 하되(`continuation: true` 선언), 씨앗 이식은 기계다.
- **좁히기**("그중에서 2023년 이후만"): 이전 인용 논문 집합을 후보로 올리고 검색 없이 다시 읽는다 — 현행 `prior_paper_ids` 경로에 `year_from`이 붙는 것뿐이다.

## 4. 검증 — 게이트와 판단 층의 경계

### 4.1 현행 게이트는 그대로

근거 한 건이 통과하는 6단 검사(논문 실재 · 인용 20자 이상 · 글자 그대로 · 앵커 블록 실재 · 인용이 그 블록 안 · 숫자가 인용문에 있음)는 **한 글자도 바꾸지 않는다.** 이것이 가장 비싼 자산이고, 판단 층은 이 위에 얹힌다.

### 4.2 판단 층 — `answer` 노드

입력은 **게이트를 통과한 근거만**이다. 번호를 붙여 준다.

```
질문: LoRA가 전체 파인튜닝보다 좋아?
질문 유형: comparison

근거:
[1] (Hu 2021, §4.2 표2) "LoRA ... 0.01% ... matches"  — 명제: LoRA는 파라미터 0.01%로 파인튜닝 성능에 도달
[2] (Dettmers 2023, §5) ...
[3] (Biderman 2024, §6.1) ...  ↔ [1]과 상충

규칙:
- 문장마다 근거 번호를 단다. 번호 없는 문장은 종합이다 — 필요할 때만 쓴다.
- 위 근거에 없는 논문·수치를 쓰지 않는다.
- 갈리면 조건을 나눠 말하고, 갈림 지점을 한 문장으로.
- 단정하지 않는다.
```

출력은 문장 단위 구조다 — 산문 한 덩어리가 아니라 `{text, refs[]}`의 목록. 이 구조가 §4.3 검사와 §8 렌더의 계약이다.

### 4.3 판단 문장 검사 — 기계식, LLM-judge 없음

게이트가 근거를 검사하듯 **답변도 기계가 검사**한다. 전부 문자열·집합 연산이다.

| # | 검사 | 실패 시 |
|---|---|---|
| A1 | `refs`의 모든 번호가 실제 근거 번호인가 | 그 문장을 **종합으로 강등** (번호 제거) |
| A2 | 번호가 붙은 문장의 **숫자**가 참조한 근거의 statement·quote에 있는가 (게이트의 `_NUMBER` 풀 재사용) | 그 문장을 종합으로 강등 |
| A3 | 답변에 **근거 목록에 없는 논문**(id·제목)이 등장하는가 | 답변 **거부** |
| A4 | 번호 붙은 문장이 **0개**인가 | 답변 거부 |
| A5 | 종합 문장 비율이 상한을 넘는가 — **시작값 50%, 실측 후 조정**(표준 수치 없음. §6 골든셋으로 정한다) | 답변 거부 |

거부되면 사유를 실어 **재생성**한다(시작값 1회, 실측 후 조정 · 비용은 예산에 계상). 재생성도 거부되면 **현행 `_narrative()`(결정론 이어붙이기)로 떨어진다** — 답은 나가되 판단 없이. C-2 fail-closed가 여기서도 성립한다: 검사를 못 통과한 판단은 화면에 가지 않는다.

강등(A1·A2)은 거부가 아니다 — 문장은 남되 "기계가 확인함" 표시를 잃는다. 거부 사유·강등 건수는 트레이스에 남고 §6 지표가 된다.

### 4.4 계약 변경

`EvidenceResult.answer`가 문자열에서 구조로 바뀐다:

```
answer: {
  segments: [ { text, refs: [n...], kind: "cited" | "synthesis" } ... ],
  checks:   { demoted: n, regenerated: bool, fallback: bool }
}
```

`claims`·`coverage`는 그대로다 — 결정론 부분은 손대지 않는다. 근거표의 행은 `claims`에서, `[n]` 번호는 `claims`의 순서에서 나온다.

**결정론 전제의 재배치**: `assemble()`은 "같은 입력이면 같은 출력"이었다. 이제 `answer`는 LLM 출력이라 그렇지 않다. 회귀 픽스처·PBT는 **`claims`·`coverage`·§4.3 검사기**에 건다(검사기는 결정론이다 — 같은 답변·같은 근거면 같은 판정). `answer` 품질은 §6 골든셋이 본다.

## 5. 실행 — 취소·진행·진입 경로

### 5.1 진입 경로를 하나로

현행은 셋이다 — 동기 JSON(끝날 때까지 침묵) / 동기 SSE / SQS 잡(폴링만). 목적("침묵 금지 · 언제든 취소")을 셋 다 만족시키려면 셋을 따로 고쳐야 하므로 **하나로 합친다**:

```
POST /api/evidence/turns      → 즉시 { sessionId, turnId }  (수락)
GET  /api/evidence/turns/{id}/events   SSE — 진행 · 부분 결과 · 완료
POST /api/evidence/turns/{id}/cancel   취소
GET  /api/evidence/turns/{id}          폴링 폴백 (SSE 끊겼을 때 복구 좌표)
```

- 턴은 **항상 백그라운드 실행**이다(LangGraph thread + Postgres 체크포인트). 실행자가 같은 프로세스의 태스크인지 SQS 워커인지는 배포 환경이 정하고 **API·이벤트 계약은 같다.** 동기 경로는 없어진다 — 수 초 걸리는 턴도 같은 길로 간다(수락 → 이벤트 → 완료).
- SSE 이벤트 형식은 novelty와 같은 `progress` 프레이밍을 유지한다(FE 파서 공유).
- **PR 2 실행 결과**: 실행자 둘(SQS 워커 `worker.py` · 프로세스 내 스레드풀 `executor.py`, SQS 미구성이면 후자)이 같은 `process_job`을 돈다. 실행 전 관문(소유권·존재·멱등)은 `_prepare_turn` 하나이고, 짧은 트랜잭션 틀은 `repository.in_transaction` 하나다 — 네 곳이 각자 베껴 쓰다 한 곳에서 롤백이 빠져 있었다. `GET /jobs/{jobId}`와 `job_id` 컬럼은 없어졌다 — 폴링·이벤트·취소가 전부 `turn_id`다. 수락은 202이고 첨부 해석(PDF 빌드 대기)은 수락 **앞**에 남아 있다(실행자로 옮기는 것은 별건). 실행자는 긴 트랜잭션을 들지 않는다 — 조회는 짧은 세션 하나, 이후 하트비트·트레이스·결과는 `TurnControl`이 호출마다 커밋한다. 이유: 트레이스 행이 flush만 되고 잡이 끝나야 커밋되면 다른 세션(이벤트 스트림)은 완료 때까지 아무것도 못 본다 — 인메모리 repo는 객체를 공유해 테스트에서 안 잡히는 종류라 실 Postgres 게이트 테스트(CI 서비스 컨테이너)로 고정했다. dispatch가 실패하면 턴을 `dispatch_failed`로 닫고 503(+쿼터 환불) — 안 그러면 커밋된 pending 행이 §5.4의 잠금이 된다.

### 5.2 취소

`cancel` 요청은 **턴 행**에 취소 플래그를 쓴다(초안은 "체크포인트에"였으나 실행 중인 스레드에 밖에서 쓰는 것은 체크포인트를 갈라놓는 바로 그 함정이라 novelty BR-RA8과 같은 행 플래그로 했다). 실행자는 **super-step 경계마다**(`decide` 진입) 하트비트를 찍으며 플래그를 읽고 멈춘다 — `heartbeat(owner_id, turn_id)` 한 문장(`UPDATE … RETURNING`)이고 owner 스코프다(INV-EV-1; 매 super-step 부르는 유일한 메서드가 격리를 못 지키면 안 된다) — 반복을 소모하지 않고 트레이스도 남기지 않는다. 진행 중인 `act`는 끝까지 돌고 그 결과도 부분 답에 들어간다(§2.8). 멈춘 시점의 상태로 `assemble`(PR 3부터 `answer → assemble`)을 돌려 부분 답을 만든다 — `stoppedReason=cancelled`, 근거 0건이면 `abstainReason=cancelled`(근거 부족과 구분). 이미 끝난 턴의 취소는 409. 실측: 취소 요청 후 28초에 부분 답(진행 중이던 추출이 끝난 뒤), 근거 8건·확인 2/16편.

### 5.3 진행

원천은 **Postgres 트레이스 행**이다 — API가 Fargate 2태스크(스티키 없음)라 프로세스 안의 큐·LangGraph 스트림으로는 재접속이 살지 않는다. `GET /turns/{id}/events?after=<seq>`는 접속 즉시 `accepted` 프레임을 보내고(수락 직후 침묵 금지), 1초 간격으로 새 트레이스 행을 `tool` 프레임으로 흘리다 턴이 종단이면 `result` 프레임(TurnOut) 후 닫는다. eventId는 `{turn}:{seq}`로 결정적이라 재접속에 같은 줄이 두 번 나오지 않는다. 조용한 구간은 15초마다 `: ping`(CloudFront 원본 유휴 30초 아래), 한 연결의 상한은 10분(넘으면 클라이언트가 `after`로 다시 붙는다). 싣는 것은 단계명·논문 제목·건수뿐이고 인용문은 싣지 않는다(C-2). `evidence.stream.first_token_ms`는 **첫 진행(tool) 프레임**까지의 지연이다 — `accepted`로 재면 동기라 구조적으로 0이고, 그러면 절대 회귀하지 않아 아무것도 못 잡는다. 폴링마다 짧은 세션을 연다 — 요청 스코프 세션을 스트림 내내 쥐면 풀 연결이 스트림 수만큼 묶인다. FE는 스트림 → `after` 재접속 3회 → `GET /turns/{id}` 2초 폴링 순으로 내려가고, 세션을 다시 열면 pending 턴에 같은 구독을 다시 붙인다.

### 5.4 세션 잠금

같은 세션에 턴이 겹치면 체크포인트가 갈라진다(Q5 조사 함정 2). 세션당 **진행 중 턴은 하나**로 제한한다 — 겹치면 409. 구현은 부분 유니크 인덱스(`evidence_turns(session_id) WHERE status='pending'`)라 두 API 태스크가 동시에 받아도 하나만 들어간다. 수락되지 않은 턴은 쿼터를 되돌린다. FE는 진행 중엔 입력을 막고 전송 자리에 취소 버튼을 둔다.

### 5.5 재실행 안전 · 고아 마감

취소·재개에서 도구가 다시 실행될 수 있다(함정 1). 검색·읽기는 부작용이 없다. **본문 승격 enqueue**만 부작용이 있으므로 paperId를 멱등 키로 쓴다(같은 논문 두 번 넣지 않음 — ingestion 큐 쪽 확인은 PR 4 재개와 함께).

**실행자가 죽은 턴**(배포·크래시): 하트비트가 `turn_stale_seconds`(기본 600 — 가장 긴 단일 단계인 승격 폴링 20초보다 충분히 크게) 넘게 끊긴 pending 턴을 폴링·이벤트·다음 수락이 발견하면 마지막 체크포인트 스냅샷으로 `assemble(INTERRUPTED)` → 부분 답(`stoppedReason=partial_failure`, 근거 0건이면 기존 기권 규칙). 조건부 UPDATE라 두 태스크가 동시에 발견해도 한 번만 쓰인다. 스냅샷이 없으면(체크포인터 없는 sqlite 개발·첫 스텝 전 죽음) `internal_error`로 닫는다. 종료 신호(SIGTERM·lifespan)는 다음 경계에서 `INTERRUPTED`로 닫고 나간다 — 실측 SIGTERM 2초 내 종료, SIGKILL 고아 턴은 재기동 후 첫 폴링에서 근거 4건의 부분 답으로 마감.

좁은 창 하나가 남는다: 재배달된 잡이 `run_loop` 진입에서 스레드를 비운 직후 죽으면 직전 스냅샷이 사라져 마감이 `internal_error`가 된다. 재개(PR 4)가 그 `delete_thread`를 걷어내면 함께 닫힌다.

## 6. 평가 — 골든셋·채점·지표

"제대로 작동한다"를 사람 느낌이 아니라 측정으로 판정한다. 틀은 업계 표준 하나다 — **문제집(골든셋) → 자동 채점 → 코드 바꿀 때마다 실행 → 실사용 지표 → 실패를 문제집에 추가.** 프로젝트마다 다른 것은 "무엇을 코드로 채점하고 무엇을 LLM 심판에 맡기느냐"뿐이다.

이 에이전트는 **"인용이 진짜인가"가 코드로 채점된다**(게이트). 보통 챗봇이 심판에 맡겨야 하는 가장 비싼 항목이 여기선 결정론이다. 그래서 무게를 코드 채점에 두고, 심판은 "판단 방향이 맞나" 하나에만 쓴다.

**시작 규모는 50문항**이다 — 유형별 균형, 각 문항에 정답 논문과 기대 판단 방향. 작성자는 사용자(논문을 아는 사람). 50이면 회귀는 잡히고, 실패 사례가 쌓이는 만큼 큰다(성숙 규모 200~500).

### 6.1 골든셋

| 유형 | 무엇을 묻나 | 정답에 들어가는 것 |
|---|---|---|
| 비교형 | "A가 B보다 좋아?" | 조건별 판단 · 갈림 지점 · 정답 논문 집합 |
| 주장형 | "X는 Y를 개선해?" | 지지/반박 판단 · 정답 논문 |
| 사실형 | "X는 언제·어디서?" | 값 · 출처 논문 |
| 후속 | 이전 턴 + 좁히기 | 좁혀진 논문 집합 |
| 코퍼스 밖 | 실시간 조회가 있어야 답할 수 있는 질문 | 정답 논문(코퍼스에 없음) |
| 범위 밖 | 잡담·코드·의견 | 검색 0회 · 안내문 |

유형별로 균형을 맞춘다. 실서비스 실패 사례는 골든셋으로 승격한다(실패 → 골든셋 루프).

### 6.2 3층 채점

| 층 | 무엇 | 어떻게 | 언제 |
|---|---|---|---|
| **1. 결정론** | 인용 실재율(=100%여야 함) · 게이트 탈락률 · 종합 문장 비율 · 반대 측 탐색 여부 · 범위 밖 질문의 검색 0회 · 정답 논문 recall@k | 코드 | **PR마다 CI** (LLM 응답은 녹화 픽스처) |
| **2. LLM 심판** | 판단이 정답과 같은 방향인가 · 조건 구분이 적절한가 · 갈림 지점이 맞는가 | 심판 모델, 채점 기준 명시. **심판 자체를 사람 라벨 표본과 일치율로 검증**한다 | 야간 / 수동 |
| **3. 사람** | 주간 표본 리뷰 | 사람 | 주간 |

검색 평가(recall@k)는 답변 평가와 **분리**한다 — 못 찾은 건지 찾고도 틀린 건지가 갈려야 고칠 곳이 보인다.

### 6.3 온라인 지표

트레이스(현행 `ToolCallRecord` + §4.3 검사 결과 + `question_kind`)에서 뽑는다: 기권율 · 취소율 · 턴당 근거 수 · 종합 비율 · 강등/거부/폴백 건수 · 실시간 조회 비율 · 첫 이벤트 지연 · 턴당 비용.

## 7. 운영 — 비용·트레이스

- **비용 권위는 U6 하나**(불변). 턴 예산 $0.50 유지, `answer`·재생성 비용 포함. 한도 도달 시 §2.9.
- **실시간 조회**는 소스별 서킷 브레이커 + 타임아웃. 한 소스가 죽어도 나머지로 진행하고, 셋 다 죽으면 코퍼스만으로 답하되 확인 범위 한 줄에 "실시간 조회 불가"를 싣는다.
- **트레이스**: 도구 호출 1:1 기록(현행) + `question_kind` + `stance` + 답변 검사 결과. 인용문·사용자 원문은 로그에 남기지 않는다(SEC-9).
- **체크포인트 보존**: 종단 턴의 스레드는 **7일**(`DOCSURI_EVIDENCE_CHECKPOINT_RETENTION_DAYS`) 뒤 정리 — 스케줄러 없이 턴 완료마다 상각해서 지우고, 세션 삭제·초기화는 그 세션 턴들의 스레드를 바로 지운다. 지운 턴에는 `checkpoints_pruned_at` 도장을 찍는다. 도장이 없으면 "오래된 종단 턴" 질의가 매번 같은 앞쪽 N건을 돌려줘 영원히 재삭제하고 그 뒤 턴은 영영 안 지워진다 — 로그의 `pruned: N`은 계속 정상으로 보인다.
