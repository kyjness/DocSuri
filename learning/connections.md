# 연결고리 복습본 — 7개 유닛이 어떻게 맞물리나

> 학습용 메모. **커밋하지 않는다.** u1~u7 개별 파일을 읽은 뒤 **전체를 한 그림으로** 묶는 복습본.
> 개별 유닛 = "한 부품이 뭘 하나". 이 파일 = "부품들이 **어떻게 맞물리나**".
> 형식: 용어는 그대로 두고 옆에 풀이. 표보다 **왜 그렇게 이어지는지**를 설명 위주로.

---

## 1. 가장 중요한 원칙 — "한 곳이 소유하고, 나머지는 빌려 쓴다"

이 프로젝트의 뼈대는 **단일 권위(single authority)** 다. = "여러 유닛이 공통으로 필요한 기능은, 한 유닛만 진짜로 가지고 나머지는 그걸 빌려 쓴다. 같은 걸 두 번 만들지 않는다." 같은 정책(예: 비용 검사)이 여러 군데 흩어지면 한 곳만 고쳐져 사고가 나기 때문에, 한 곳에 몰아둔다.

누가 무엇을 **진짜로 소유**하는지:

| 능력 | **소유자(단일 권위)** | 빌려 쓰는 쪽 | 한 줄 설명 |
|---|---|---|---|
| 검색 근거화 `enforce` | **U6** `GroundingEnforcementHook` | U2 (gateway seam에서 호출) | "검색 결과가 진짜 검색된 레코드냐"를 검사 |
| 비용 가드 | **U6** `CostGuardCircuitBreaker` | U2·U7 (읽기만) | 돈 얼마 썼는지 보고 저하 모드 결정 |
| 관측(텔레메트리) | **U6** `ObservabilityHub` | 전 유닛 (비차단) | 지표·로그를 한 곳에 모음 |
| principal 주입 | **U6** 게이트웨이 auth | U2·U4 (읽음) | 쿠키→신원 복원해서 `request.state`에 심음 |
| 소유권/관리자 인가 | **U3** `AuthorizationGuard` | U4 (위임) | "이거 네 거 맞아 / 너 관리자야" 판정 |
| 세션 발급/검증 | **U3** `SessionManager` | U6 게이트웨이 | 로그인 상태 만들고 확인 |
| 코퍼스 인덱스 | **U1** writer (유일) | U2 reader (유일) | 검색 대상 데이터를 쓰고/읽음 |
| 전문 저장(S3) | **U1** 적재 | U7 (요약 소스로 읽음) | 논문 원문 보관 |
| 계약(DTO·이벤트·벡터) | **shared/** (SSOT) | 전 유닛 | 주고받는 데이터 모양의 약속 |

- **enforce** = 근거화를 "강제(검열)"하는 단계. *근거화(grounding)* = 결과가 실제 데이터에 뿌리를 두는지 확인(없는 걸 지어내는 *환각* 방지).
- **principal** = 이 요청의 주인 정보(user_id·role 등).
- **SSOT** = Single Source Of Truth, "하나의 진실 출처".

→ **외우면 좋은 한 줄**: *횡단 관심사(검문·비용·관측)는 U6, 인가·세션은 U3, 데이터는 U1이 소유. 나머지는 빌려 쓴다.*

## 2. 시나리오 A — "검색 한 번"이 7개를 어떻게 관통하나

로그인된 사용자가 "그래프 신경망 추천"을 검색할 때:

```
[U5] SearchScreen — validateQuery(NFC·≤500) → ApiClient.search
       │  (토큰은 안 보냄; httpOnly 쿠키만)
       ▼
[U5] BFF (서버 전용) — 쿠키를 서버↔게이트웨이 구간에서만 첨부
       ▼
[U6] 게이트웨이 — ① request_id ② rate-limit ③ 쿠키→[U3]verify→principal 주입
       ▼
[U2] plan_and_retrieve:
       ② [U6]비용상태 읽어 저하모드 결정
       ③ 임베딩(Bedrock search_query) — 캐시 미스면 호출
       ④ OpenSearch docsuri-corpus-v1 (★[U1]이 채운 인덱스) k-NN∥BM25 → RRF → 디덥
       ⑤ top_n=20
       ⑥ 근거 입력 구성
       ─ seam ─
       ⑦ [U6]GroundingEnforcementHook.enforce → pass/block/abstain
       ⑧ 카드 7필드 조립 (raw 점수 비노출)
       ⑨ SearchExecuted 발행 (fire-and-forget)
       ▼                                   ▼
   [U5]로 응답                        [AWS EventBridge]
   classify→렌더                           ▼
                                  [U4] record_search (dedupe_key 멱등) → PostgreSQL
```

**여기서 만나는 연결**:
- 요청 경로 = U5 → U6 → U2. 그 위에 U3(세션 검증)·U1(읽는 인덱스)·U6(근거화·비용)·U4(이력, 비동기)가 다 얹힌다.
- **제일 중요한 한 쌍**: U2 ⑨가 던진 이벤트를 **받는 쪽 = U4 ⓑ**. 그래서 —
  - U2의 **fire-and-forget** (= 결과 안 기다리고 던지고 잊음. 이력이 늦거나 실패해도 검색 응답엔 영향 0) 과
  - U4의 **at-least-once + dedupe_key** (= 이벤트 버스는 같은 메시지를 두 번 보낼 수 있어서[at-least-once], `owner|시각|query`의 sha256을 키로 중복을 걸러 딱 한 번만 저장)
  - 이 둘이 **맞물려 한 쌍**이다. (보내는 쪽은 가볍게 던지고, 받는 쪽이 중복을 책임진다.)

## 3. 시나리오 B — "요약 한 번" (U7이 다른 유닛에 기대는 법)

검색 결과 카드에서 "요약 보기":

```
[U5] 결과카드 → ApiClient.summarize → BFF → [U6] 게이트웨이(principal)
   ▼
[U7] orchestrator:
   ⓪ 캐시(Redis+S3) HIT → 즉시 반환 (LLM 0회)
   ① [U6]비용 게이트 — degrade/OPEN이면 중단
   ② 소스 = S3 전문 (★[U1] ⑥이 적재한 그것) / 없으면 초록
   ⑥ Bedrock 생성 (Sonnet/Haiku)
   ⑦ ★U7 자체 근거화 (← U6 enforce 아님!)
   ⑨ S3+Redis 캐시 저장
```

U7이 빌려 쓰는 것: **① 비용**(U6) · **② 전문**(U1이 S3에 적재한 것) · **진입 principal**(U6). 즉 U7은 혼자 다 하는 게 아니라 U1·U6에 기댄다.

**여기서 제일 헷갈리는 것 — 근거화가 둘이다:**

| | **U6 enforce** (U2가 씀) | **U7 자체 grounding** |
|---|---|---|
| 검사 대상 | 검색 후보 식별자 ⊆ 검색 레코드 **집합** | 요약문 ⊆ **한 논문의 원문** |
| 종류 | SET 멤버십 (목록에 있냐) | 문서 충실도 (원문에 충실하냐) |
| 소유 | U6 (단일 권위) | U7 (자기 소유) |
| 방식 | — | 결정적(수치 95.3%↔0.953 등), LLM-judge 없음 |

→ "근거화 단일 권위 = U6"라는 말은 **검색 근거화에 한정**해서 맞다. 요약 근거화는 **종류가 다른 검사**(한 논문 원문에 충실한가)라서 U7이 따로 가진다. **이거 하나만 기억하면 됨.**

## 4. 시나리오 C — "저장된 검색 재실행" (백도어 금지의 의미)

```
[U5] → [U4] rerunSavedSearch
   [U4] authorize_owned (← [U3] 가드에 위임)
   [U4] SearchGatewayPort.search → ★[U6] 게이트웨이 재진입 → [U2]
        (U2 직접 호출 금지! 비용 가드·근거화를 매번 재적용)
```

**왜 빙 도나**: U4가 U2를 **직접** 부르면, U6 게이트웨이의 검문(비용 가드·근거화 enforce)을 **건너뛰는 지름길 = 백도어(뒷문)** 가 생긴다. 비용 한도가 걸려 있어도 이 경로로는 안 걸리는 구멍이 난다. 그래서 재실행도 **정문(게이트웨이)으로 다시 들어가** 시나리오 A의 검색 경로를 **그대로** 다시 탄다. (INV-L2 = 라이브러리 불변식 2번.)

## 5. 시나리오 D — "논문 색인" (U1이 백그라운드에서 코퍼스 채우기)

사용자 경로 **밖**에서 도는 워커. 시나리오 A의 ④가 읽는 인덱스를 **여기서 만든다**:

```
[U1] 트리거(증분/이벤트/재빌드) → SQS
   워커 → ingest_one:
     ③ 라이선스(CC-BY)·검증·철회 게이트
     ⑥ 전문 → S3 (★[U7]이 시나리오 B ②에서 읽을 것)
     ⑧ 임베딩 (Bedrock search_document ← U2의 search_query와 같은 공간)
     ⑨ IndexRecord 조립 (★[U2]가 읽을 바로 그 모양)
     ⑩ OpenSearch docsuri-corpus-v1 (★[U2] reader가 읽는 그 인덱스)
```

**writer/reader 불변식**: U1(쓸 때 `search_document`로 임베딩) / U2(읽을 때 `search_query`로 임베딩)가 **같은 벡터 공간**(`shared/vector-spec`: 모델·1024차원·cosine)을 공유해야 검색이 유효하다.
- **불변식(invariant)** = 항상 지켜야 하는 약속. 한쪽만 바꾸면 벡터가 어긋나 검색이 통째로 깨지므로, vector-spec이 이 약속을 양쪽에 강제한다.

## 6. 세션 하나의 일생 (U3 → U6 → U2/U4)

```
[U3] 로그인 성공 → token_hex(32) 발급 → Redis 저장 → httpOnly 쿠키로만 전달(SEC-12)
   ▼ (이후 모든 요청)
[U6] 게이트웨이 ⓐ③ — 쿠키 꺼내 [U3]session_manager.verify → principal 복원
   ▼
[U2]/[U4] — request.state.principal 읽어서 "이 요청의 주인" 사용
   (Redis 장애 → U3·U6 둘 다 401 fail-closed, DB 폴백 안 함)
```

→ U3은 **만들고**(issue), U6은 **검증해 푼다**(verify→principal), U2/U4는 **쓴다**(읽기). 셋이 한 줄로 이어진다.
- **fail-closed** = 애매하거나 고장 나면 통과시키지 말고 거부. Redis(세션 저장소)가 죽으면 "확실치 않으니" 401로 막는다(위험하게 열어두지 않음).
- ※ pipeline.md에 한때 "U6 auth 미결선"이라 적혀 있었으나 **실제로는 결선됨**(`backend/middleware/auth.py`) — 학습 중 발견해 수정함.

## 7. 모든 유닛에 반복되는 패턴 (한 번 알면 7번 보인다)

개별 유닛에서 따로 본 것들이 사실 **같은 원리의 반복**이다. 이걸 알면 새 유닛도 "아, 또 그거네" 하고 빨리 읽힌다.

- **포트/어댑터 + mock-first** — 도메인은 "이런 능력이 필요해"라는 인터페이스(포트)만 알고, 실제 구현(OpenSearch/Bedrock/S3)은 배선이 꽂는다. 덕분에 진짜 인프라 없이 가짜로 바꿔 끼워 개발. U2(포트)·U5(Transport seam)·U7(adapters) 전부 같은 발상.
- **fail-closed** — 애매하면 막는다. U2(인덱스 장애→503)·U3/U6(Redis→401)·U4(타인→404)·U7(예외→abstain).
- **단일 권위** — 정책은 한 곳에서만. U6(횡단)·U3(인가)·U1(writer)·shared(계약).
- **멱등(idempotent)** — 같은 일 두 번 해도 한 번과 같음. U1(chunkId·dedup)·U4(add·dedupe_key)·U6(event_id)·U7(캐시 키).
- **SEC-9 비노출** — 내부 정보(점수·존재 여부·토큰)를 사용자에게 안 흘림. U2(raw 점수)·U4(타인→404)·U7(tokens/cost)·U5(비기술 에러).
- **레이턴시 vs 처리량 — 정반대 두 자세** — 사용자가 기다리는 작업(U2 검색·U7 요약)은 문제 생기면 **빨리 포기**해 화면이 안 멈추게. 백그라운드 작업(U1 색인)은 안 기다리니 **끈질기게 재시도**(5회). 같은 "실패 대응"인데 *누가 기다리느냐*에 따라 반대로 군다.
- **at-least-once + dedup** — 이벤트는 중복 올 수 있으니(at-least-once) 멱등키로 흡수. U4(dedupe_key)·U6(인시던트 발행)·U1(SQS 재배달).

## 8. shared/ 계약이 묶는 이음매 (유닛 경계의 "표준 규격")

유닛끼리 직접 코드를 안 부르고 **shared/의 약속된 모양**으로만 소통한다:

| 계약 | 만드는 쪽 → 읽는 쪽 | 무슨 모양 |
|---|---|---|
| `IndexRecord` (vector-spec) | U1 씀 → U2 읽음 | 논문 한 청크의 모양 |
| `SearchRequest/Response` (dtos) | U5 ↔ U2 | 검색 요청·응답 |
| `SearchExecutedEvent` (events) | U2 발행 → U4 소비 | "검색이 일어났다" |
| `GroundingDecision`·`BudgetState` (ports) | U6 → U2/U7 | 근거화 판정·비용 상태 |
| vector-spec 상수(1024·cosine) | U1·U2 동일 강제 | 임베딩 공간 규격 |

→ 그래서 한 유닛 **내부**를 바꿔도 이음매(계약)만 지키면 다른 유닛은 무영향. 이게 "모듈러 모노리스"의 *모듈러*(= 유닛을 따로따로 짤 수 있음)를 떠받치는 힘이다.

## 9. 한 문장 총정리

> **U1**이 채운 코퍼스를 **U2**가 검색하고, **U6**가 길목에서 검문(인증·비용·근거화)하며, **U3**가 누구인지 보증하고, **U4**가 결과를 저장·기록하고, **U7**이 논문을 깊이 읽어주며, 이 모두를 **U5**가 토큰을 가둔 채 화면에 띄운다 — 그리고 그 사이는 전부 **shared/ 계약**으로 이어져 있다.
```
